## 0. 一句话

**深色 canvas 的取值本身不是 B24 的解药。** 复算：把 canvas 从现状 `L=0.0102` 一路提到 su.700 的 `L=0.0501`（明度翻五倍），浅色卡叠深底上的 tertiary 对比度只从 **2.49** 动到 **2.54** —— 因为那一层的明度由玻璃卡的 alpha 决定，canvas 只是它下面千分之二的一点偏移。

所以 A2 我能交付的是两件事：**深色表面族换族到 su 青灰** + **深色色晕定值**。B24 的归属要从 A2 改成 B22（见 §7）。

## 2. §12.2 两处输入的更正（2026-10-04 已采纳，见 R1 / R2）

### 2.1 「secondary 3.42」在深色端不可能出现

- `#A4BCCB`（L=0.4817）**恒亮于** `#839EB0`（L=0.3241）；
- 在任何一个亮底上，越亮的字对比度越低 → **深色 secondary 的对比度必然小于 tertiary**；
- §12.2 给的却是 secondary **3.42** > tertiary **2.40**。这两个数不可能出自同一组「深色字阶 × 同一背景」。

我复算能对上的只有 tertiary 那一半：

| 底 | 合成后 | L | tertiary `#839EB0` |
| --- | --- | --- | --- |
| `#FFFFFFF0` 叠 `#0A1B2A` | `#F1F2F2` | 0.8833 | **2.49** |
| `#FFFFFFDB` 叠 `#0A1B2A` | `#DCDFE1` | 0.7339 | **2.10** |

**处理**：该行按「待验证」处理，由 M0 断言统一产出（与 §10.2-7 一致），**不要在它上面取设计值** —— 包括不要把 3.42 当作「secondary 也需要修」的依据。深色 secondary 是否需要动，取决于 §5 的表，不取决于这个数。

### 2.2 「浅色玻璃卡 `#FFFFFFF0`」不是玻璃，是浅色端卡片

`#FFFFFFF0` = `semantic.light.surface.card`（浅色端卡片，94% 白）；浅色玻璃是 `semantic.light.surface.glass` = `#FFFFFFB3`（70%）。两者差 24 个 alpha 点，合成到深底上差 **0.15 L**（0.883 vs 0.734），tertiary 差 0.39 个对比度档。

**处理**：§12.2 该行改写为「浅色端卡片 `surface.card` 叠深底」，或补上玻璃档位。不指名道姓，M0 出来的还会是一组对不上的数。

## 3. 深色 canvas / surface 族目标色值

**只改色相，不动明度阶梯。** 现状的明度关系没有被任何一轮评审质疑，动它会连带 37 个组件的深色观感整体改变；换族则不产生这个风险。

| 令牌 | 现状 | 色相 | → | 提案 | 色相 | ΔL |
| --- | --- | --- | --- | --- | --- | --- |
| `semantic.dark.bg.canvas` | `#0A1B2A` | 208.1° | → | **`#0A1B26`** | 203.6° | −0.0003 |
| `semantic.dark.bg.grouped` | `#0D2334` | 206.2° | → | **`#0D2331`** | 203.3° | −0.0003 |
| `semantic.dark.surface.card-sunken` | `#0A1E2C` | 204.7° | → | **`#0A1E2A`** | 202.5° | −0.0001 |
| `semantic.dark.surface.card-solid` | `#0C2130` | 205.0° | → | **`#0C212D`** | 201.8° | −0.0002 |
| `semantic.dark.surface.card` | `#14283AD1` | 208.4° | → | **`#132836D1`** | 204.0° | −0.0005 |

### 3.1 色相选择理由（§12.3-1 要求）

1. **现状是三套色温。** 深色表面族 204.7–208.4°、su 深段 200.7–204.7°、深色渐变族 198.0–202.9°。三套各占一段，**只有深色表面族跑到了 205° 以外** —— 这就是"深色端看着比浅色端更冷、偏靛"的物理来源。
2. **收到 202–204° 后**，深色表面族落在 su 深段与渐变族的交叠带上，与 su.900 的色相差 ≤ 3°，"深色端和浅色端是一个族"这句话第一次可以量化。
3. **对「200–203° 是否必须」的明确回答：不是。** 按 200–203° 卡死的话，su.700（203.3°）、su.950（204.7°）、浅色 canvas（193.3°）全都越界，而这三处都没有出过观感问题。要守的是「**同族**」，不是「同一个数字」。写成数字会误导实现侧去微调不该动的地方。
4. **零明度风险。** 五条提案的 |ΔL| ≤ 0.0005。这不是"深色端调亮/调暗"，是纯换族。
5. **后续联动**：`surface.glass` 的两个候选（`#0A1A28` = 208.0°、`#0C2038` = 212.7°）同样跑出族外，B22 裁定唯一真源时应一并收到 203° 带内（建议 `#0A1A24` 位）。**但玻璃取哪一档是 B22 的裁定，不在本提案内。**

## 4. 深色色晕

### 4.1 写法

**净 alpha。** 令牌里写的 alpha 就是渲染时的 alpha，**不允许**再乘 preview 里的 `opacity:.55` / `.5`（B23 的教训）。几何与浅色版**逐字一致** —— 同 3 个位置、同 3 个半径、同 3 个 transparent 收口，只换颜色与 alpha。这样生成器只需产出「颜色 + alpha」两组数，两端与深浅两态共用一套几何。

```css
/* 深色色晕 · 提案 v0.1（净 alpha，几何同浅色版） */
radial-gradient(90%  62% at 12%  -6%,  rgba( 18, 52, 73,.30), transparent 62%),  /* 渐变族起 #123449 */
radial-gradient(82%  58% at 92%   2%,  rgba( 15, 64, 85,.20), transparent 64%),  /* 渐变族止 #0F4055 */
radial-gradient(120% 74% at 58% 104%,  rgba( 22,119,179,.08), transparent 68%);  /* 品牌蓝   #1677B3 */
```

### 4.2 alpha 的取值依据

深色底找**最亮**（§12.4）。三条径向在页面中部会叠加，最不利底是**三条都命中**的那块。备选与结果：

| 净 alpha（湖蓝位 / 天青位 / 品牌位） | 最亮合成底 | L | tertiary 最不利 | 判定 |
| --- | --- | --- | --- | --- |
| 36 / 26 / 10（§12.2 候选的放大版） | `#0E3347` | 0.0291 | 4.73 | ✅ 余量 < 5% |
| **30 / 20 / 8（推荐）** | `#0E2F42` | 0.0249 | **5.00** | ✅ 余量 11% |
| 26 / 18 / 7（更保守） | `#0D2D3F` | 0.0229 | 5.13 | ✅ 余量 14% |

推荐 **30 / 20 / 8**：tertiary 留 11% 余量，同时色晕在深色底上仍然看得见（canvas `#0A1B26` → 最亮处 `#0E2F42` 是可辨识的一档）。

### 4.3 与浅色端的耦合（B23）

**本节 v0.2 更正**：v0.1 用"单个色标 × 单档 alpha"估过一版（3.80 / 5.73），口径不严谨 —— 色晕是三条径向叠在一起，必须按真实几何合成。下面换成 **601×601 几何采样**：椭圆半径与圆心取自 `01-foundation` §3.6 与 `preview:1381-1383`，逐像素合成后取**最暗点**（浅色底找最暗），premultiplied 插值。

「42%」之所以要问，是因为它到底落在哪一层没写清。同一句话有六种读法：

| 读法 | 谁乘谁 | 生效 alpha（湖/天/群） | 最暗采样点 | `#4C616D` | `#5B7784` |
| --- | --- | --- | --- | --- | --- |
| **现状** | 66/46/18 × `opacity .55` | 36.3 / 25.3 / 9.9 | `#D4EBEF` L=0.7958 | 5.22 ✅ | 3.83 ❌ |
| A 42 = 第一档 alpha | 42/46/18，无乘子 | 42 / 46 / 18 | `#BCE0E6` L=0.6984 | 4.62 ✅（余量仅 2.7%） | 3.39 ❌ |
| B 42 = 浓度，等比缩放 | × 42/66 | 42 / 29.3 / 11.5 | `#CFE9ED` L=0.7763 | 5.10 ✅ | 3.74 ❌ |
| C 42 = 最深那一档 alpha | 66/46/42，无乘子 | 66 / 46 / 42 | `#B1CFDD` L=0.5907 | **3.96 ❌** | 2.90 ❌ |
| D 42 = 净 alpha 乘子 | × 0.42 | 27.7 / 19.3 / 7.6 | `#DBEEF2` L=0.8258 | 5.41 ✅ | 3.97 ❌ |
| **E 设计侧：令牌直接写净 alpha** | 无乘子 | **23 / 16 / 6** | `#DFF0F3` L=0.8426 | **5.53 ✅** | 4.04 ❌ |

**四条结论**：

1. **只有读法 C 会翻车**（`#4C616D` 3.96 ❌）。它就是把 42% 加到群青那一档 —— 而这是第一轮"3.80"的来源。
2. **读法 A、B 虽然达标，但都比今天更深**（L 0.698 / 0.776，现状 0.796），与用户三次"再浅一点"**反向**，不能取。
3. **`#5B7784` 在任何浓度下都不达标**（最高 4.04；连裸 canvas 也只有 4.43）。所以 **B10 必须换值，与 B23 无关** —— 这更正了本文 v0.1「两者必须同批裁定」的说法。
4. **真正的耦合只剩一条**：若 B23 取读法 C，则 `#4C616D` 也不够（3.96），要压到 `#41565F`（4.71 ✅）。

**推荐读法 E**：令牌直接写净 alpha 23 / 16 / 6，删掉 `preview:1423` 的 `opacity:.55` 与 `preview:1468` 的 `.5`。理由是它同时满足两条约束 —— 比现状浅一档（L 0.7958 → 0.8426，符合"再浅一点"），且 `#4C616D` 留 22% 余量。

**余量是刻意留的**：读法 A（66/46/18 全量生效）是"不换 tertiary 还能过"的天花板，只有 2.7% 余量；色晕之上还会叠卡片、浮层、临时遮罩，M0 的断言必须按最不利自动取，所以不能贴着 4.5 走。

> 顺带记一条待清的真源问题：`preview` 里其实有**两套色晕**——`1381-1383`（66/46/18，`opacity:.55`）与 `1449-1451`（80/88/40，用于"抬升行"）。第二套比第一套浓一倍，也没进任何令牌。B23 落盘时应一并裁定是删还是并入 `wash` 组。

## 7. B24 归属更正（2026-10-04 已采纳，见 R5）

**复算事实**：canvas 取任何可行值，浅色卡叠深底上的深色字阶对比度几乎不动。

| canvas | 卡面 L | primary | secondary | tertiary |
| --- | --- | --- | --- | --- |
| `#0A1B2A`（现状） | 0.8833 | 1.02 | 1.76 | 2.49 |
| `#0A1B26`（提案） | 0.8831 | 1.02 | 1.75 | 2.49 |
| `#1B2E38`（su.800，极端提亮） | 0.8922 | 1.03 | 1.77 | 2.52 |
| `#2C4250`（su.700，极端提亮） | 0.9019 | 1.04 | 1.79 | 2.54 |

**结论**：B24 不是"A2 定值后就能关"的项。它的物理成因是「**深色端字阶落到亮底上**」，只有两条路能真解决：

1. **给深色端浮层加亮度地板**（玻璃/卡片在深色端必须保证合成后仍是深色）—— 归 B22；
2. **给这类底配一套亮底字阶**（`text.on-light.*`，见 §6）—— 本提案建议新增，值为浅色端字阶的别名。

**建议**：B24 的处理栏从「等 A2 定值」改为「**挂在 B22；A2 交付后即可并行推进，不互为前置**」。这样 M0 的四项前置里，A2 与 B22 变成两条独立线，少一个串行点。

## 9. D1 深色段令牌（已落盘）

### 9.1 改值（5 条，纯换族）

```jsonc
// semantic.dark —— 只改色相，明度阶梯不变
"bg": {
  "canvas":  { "$value": "#0A1B26" },   // was #0A1B2A  H 208.1° → 203.6°
  "grouped": { "$value": "#0D2331" }    // was #0D2334  H 206.2° → 203.3°
},
"surface": {
  "card":        { "$value": "#132836D1" },  // was #14283AD1  H 208.4° → 204.0°
  "card-solid":  { "$value": "#0C212D"   },  // was #0C2130    H 205.0° → 201.8°
  "card-sunken": { "$value": "#0A1E2A"   }   // was #0A1E2C    H 204.7° → 202.5°
}
```

### 9.2 新增（深色色晕，3 色标 + 净 alpha）

```jsonc
// 顶层新增 wash 组（与 gradient 平级，不要放进 semantic.*.gradient）
"wash": {
  "light": {
    "$type": "gradient",
    "$value": "radial-gradient(90% 62% at 12% -6%,rgba(176,213,223,.23),transparent 62%),radial-gradient(82% 58% at 92% 2%,rgba(126,196,207,.16),transparent 64%),radial-gradient(120% 74% at 58% 104%,rgba(76,141,174,.06),transparent 68%)",
    "$description": "浅色页面色晕。数值 = 生效 alpha（净 alpha），渲染时不得再乘 opacity；同步删除 preview:1423 的 opacity:.55 与 preview:1468 的 .5。本值为设计侧推荐（§4.3 读法 E），最终以 B23 裁定为准。"
  },
  "dark": {
    "$type": "gradient",
    "$value": "radial-gradient(90% 62% at 12% -6%,rgba(18,52,73,.30),transparent 62%),radial-gradient(82% 58% at 92% 2%,rgba(15,64,85,.20),transparent 64%),radial-gradient(120% 74% at 58% 104%,rgba(22,119,179,.08),transparent 68%)",
    "$description": "深色页面色晕。几何与浅色版逐字一致，只换颜色与 alpha。净 alpha 30/20/8，最不利 tertiary 5.00:1。"
  }
}
```

> ⚠️ **给架构师的 D1/D2 提示**：`build.js` 的 `collectGradients()` 会遍历 `semantic.light.gradient` / `semantic.dark.gradient` / 顶层 `gradient` 三处，并对每个值调用 `parseLinearGradient()`。若把色晕按 §7.1 D1 的字面写法落进 `gradient.wash.light/dark`，生成器会直接抛错。**两条可行路径**：(a) 色晕另起 `wash` 组、由 D4 的 `gallery.js` 消费（推荐，不动生成器）；(b) D2 给生成器加 radial 解析。二者都行，但不能按原字面落。

### 9.3 新增（亮底字阶 3 条）——落盘时改为**平铺键**，不是嵌套组

提案原写的是 `semantic.dark.text.on-light.{primary,secondary,tertiary}`（嵌套）。**实际落盘改成平铺的兄弟键**，两端各主题都写一份：

```jsonc
"text": {
  "primary":            { "$value": "#0A1B24" },
  "secondary":          { "$value": "#3E5764" },
  "tertiary":           { "$value": "#4C616D" },
  "on-light-primary":   { "$value": "#0A1B24" },
  "on-light-secondary": { "$value": "#3E5764" },
  "on-light-tertiary":  { "$value": "#4C616D" },
  "on-soft":            { "$value": "#123F5C" },
  ...
}
```

**为什么改**：`build.js` 用 `Object.keys(t.semantic.light[group])` 当作两端的键集（`build.js:154-166`、`306-315`），并逐键读 `.$value`。嵌套的 `on-light` 是个没有 `$value` 的对象 → Swift 侧静默漏掉，**Kotlin 侧 `kotlinColor(undefined)` 直接抛错**。支持嵌套要动 D2（两端的解析路径也要跟着改），**M0 不值得**；平铺键零改动即可生成，键名自然得到 `textOnLightPrimary` / `textOnLightSecondary` / `textOnLightTertiary`。

**代价**：浅色主题下这三个键与 `primary/secondary/tertiary` 同值，是为"两端成对生成"而存在的冗余。用 `contrast.js` 一条断言兜住漂移 —— 「`*text.on-light-*` 必须等于同名去掉前缀的 `*text.*`」。

**影响面**：两端各新增 3 个公开入口。iOS 侧已随生成更新；**Android 侧 `api/wisdom-ui.api` 现在是陈旧的（`WDColors` 27 参 → 30 参），`apiCheck` 会红**，需在 Android 仓库跑一次 `apiDump` 并与令牌改动同一次提交（B19 的纪律）。
