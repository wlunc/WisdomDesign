## 1. 架构师：审阅结论与两端实施计划

> 发言要点：设计本身成熟度很高，规格可执行度也高；但有四类「账目不实」必须先修，否则两端会照着一份过不了自己无障碍底线的规范开工。

### 1.1 审阅范围与方法

| 做了什么 | 怎么做的 |
| --- | --- |
| 读全部规范 | `docs/01`–`09`、`docs/specs/01`–`03` 全文 |
| 核对令牌 | `tokens/wisdom.tokens.json` 168 个叶子令牌逐个建档 |
| 实测对比度 | 按 WCAG 2.1 相对亮度公式，复算规范里所有声称的对比度 |
| 核对一致性 | 脚本抽取规范里的令牌引用，与令牌文件比对；再与画廊 `--g-*`、生成产物三者互校 |
| 看设计稿 | 无头 Chrome 渲染 `design/preview` 与三份画廊，浅深并排逐屏核对 |
| 验证工程状态 | `node tools/token-build/build.js --check`（通过）、两端源码与构建配置 |

### 1.2 评审结论

| 对象 | 判定 | 说明 |
| --- | --- | --- |
| 设计语言（温和蓝 / Liquid Glass / 家庭工具调性） | ✅ 可直接实施 | 方向清晰、自洽，六个风格特征都能落到具体规格 |
| 组件规格 `specs/01–03` | ✅ 可直接实施 | 12 节模板 + 可勾选验收项；是一份扎实的、能当开发契约的规格 |
| 令牌结构（原始 / 派生 / 语义三层） | ✅ 结构对 | 分层正确，生成器可跑通 |
| 对比度账目 | ⚠️ 需先修 | 多处声称值与实测不符，其中 3 处突破规范自己的 4.5:1 底线 |
| 单一真源 | ⚠️ 需先修 | 同一个数值存在「令牌 / 规格 / 画廊」三个来源，已出现漂移 |
| iOS Foundation | ⚠️ 需先修 | 生成的字阶是固定字号，**不随动态字体缩放**，与 AX3 硬门槛直接冲突 |
| `docs/03-platform-mapping.md` | ❌ 需重写 | 仍是旧版绿色品牌（`#2F7F63`）、旧命名（`Wd*`）、旧路径，通篇与 v1.0 无关 |
| 工程化（CI / 门禁） | ❌ 缺失 | 三个仓库都没有 `.github`，令牌一致性与对比度没有任何自动校验 |

### 1.3 先立住：做得好、不要动的六件事

1. **令牌分层是真的分层。** `color.su.*` 只作中性阶、`derived.*` 只由色卡派生、界面只准用 `semantic.*`——守住这条纪律，跨端一致性就有保障。
2. **`semantic.light / dark` 的渐变拆法正确。** 两端渲染方式不同（SwiftUI 动态色一条令牌搞定，Compose 需要两套实例），文档点明了这个差异，是踩过坑才写得出来的话。
3. **规格里的「不要用」比「用」有价值。** Button / Switch / Checkbox / Radio 都写了反例和替代组件；Switch 那条「打开后还要再点一次确认，就不该用 Switch」能直接消掉一类设计争论。
4. **无障碍写成了硬门槛而不是原则。** 四条底线 + iOS 44pt / Android 48dp 的显式区分，比多数设计系统认真。
5. **令牌流水线真的能跑。** `--check` 通过，CSS 角度渐变被正确换算到 SwiftUI / Compose 两端的坐标系，生成产物与源一致。
6. **画廊浅深并排。** 「深浅色的问题大多出在只调了浅色」——这个做法确实最省事。

### 1.4 开工前必须修的阻塞项（B1–B9）

#### B1. 对比度账目错误，且已突破自己的 4.5:1 底线

实测复算（WCAG 2.1，脚本见附录 B）：

| 组合 | 规范声称 | 实测 | 判定 |
| --- | --- | --- | --- |
| 湖水蓝 `#B0D5DF` / `text.on-soft` `#123F5C` | 13.6:1 | **7.10:1** | 通过，但账面虚高近一倍 |
| 天青 `#7EC4CF` / `#123F5C` | 10.5:1 | **5.65:1** | 同上 |
| 群青 `#4C8DAE` / `#123F5C` | 5.8:1 | **3.03:1** | ❌ 不达标 |
| 海青 `#080F40` / 白 | 17.1:1 | 18.22:1 | 通过，账面偏低 |
| 景泰蓝 `#2A5CAA` / 白 | 6.7:1 | 6.54:1 | 通过 |
| 浅填充 `#8FCFDD → #63BAD2` / `#0E3A55` | 5.4–6.9:1 | 6.92 / 5.40:1 | ✅ 这一条是准的 |

问题出在 `01-foundation` §3.1 的「深字对比」整列：三个值全部对不上，规律像是按更深的文字色（接近 `#0A1B24`）算的。危害不在数字本身，而在：

- 群青 `#4C8DAE` 被归为「只配深色文字」，实际只有 3.03:1。设计师照这条拿它做底 + 深字，直接违规。**建议把它降级为描边 / 图形专用色**，与石青 `#1685A9` 同级，并补进 §3.5 规则二。
- 湖水蓝写成 13.6 会让人以为还有余量，实际 7.10 已经不允许再叠白或提亮。

#### B2. 三处浅色语义色在自带浅底上不足 4.5:1

`semantic.light.status.*` 配 `status-soft.*` 是 `WDBanner`（P0）的默认组合，而 `docs/06` 第 2 条底线就是「正文对比度 ≥ 4.5:1」：

| 组合 | 实测 | 判定 |
| --- | --- | --- |
| 成功 `#2A7F5C` on `#E3F5EC` | 4.32:1 | ❌ |
| 信息 `#1677B3` on `#E1F0F8` | 4.17:1 | ❌ |
| 警示 `#97651F` on `#FFF4DC` | 4.58:1 | ⚠️ 刚过 |
| 危险 `#B8564D` on `#FBE7E4` | 3.94:1 | ❌ |

深色端全部 7.5–9.2:1，没有问题。**建议**：保留 `status.*` 给图标 / 圆点 / 填充（配白字均 ≥4.7），新增一组仅用于浅底文字的 `status-text.*`：成功 `#226A4C`（5.73）、信息 `#125F8F`（5.89）、警示 `#8A5A18`（5.41）、危险 `#9E4038`（5.44）。这四个值配白字仍 ≥5.6:1，填充场景不受影响。

#### B3. 深色版按键文字色不达标

Button 变体表写 `filled` 文字用 `text.on-fill`，而 `semantic.dark.text.on-fill = #DCEEF4`：

| 组合 | 实测 |
| --- | --- |
| `#DCEEF4` on 深色填充起点 `#1677B3` | **4.07:1** ❌ |
| `#FFFFFF` on `#1677B3` | 4.86:1 ✅ |

画廊里深色端实际写的是白字（`--g-on-fill: light-dark(#0E3A55, #FFFFFF)`），也就是**规范和令牌在打架，画廊选了另一条路**。建议令牌改为纯白 `#FFFFFF`（或 `#F2F9FC`，4.56:1），并让画廊 `--g-on-fill` 与令牌对齐。

#### B4. `gradient.mid` 上的白色小标记只有 2.51:1

`gradient.mid (#4FB0C8 → #1685A9)` 是开关轨道、Checkbox 填充、Radio 圆点的底色，上面压的是**白色**勾 / 滑块 / 圆点。图形与边界门槛是 3:1，起点 `#4FB0C8` 只有 2.51:1。

**建议**：起点改 `#3FA0BC`（3.01）或更稳的 `#3898B4`（3.32）。改完仍是「轻量小面积标记」的观感，白勾才立得住。

#### B5. 同一个数值有多个来源，已经漂移

| 数值 | 令牌 | 规格 / 布局 | 画廊 | 一致 |
| --- | --- | --- | --- | --- |
| Tab 栏高度 | `size.tabbar-height` **56** | `02-advanced` §34 与 `09-layout` 均写 **58** | 58 | ❌ |
| 深色按键文字 | `#DCEEF4` | 规格正文说「配白字」 | `#FFFFFF` | ❌ |
| 玻璃填充 | `glass` 70.2% / `glass-strong` 85.9% | `01-foundation` §7.2 写「导航栏 62%、Tab 62%、浮层 82%」 | 70% / 88% | ❌ |
| 遮罩 | 无令牌 | `09-layout`「页面底色 40% 黑」 | — | ⚠️ 未令牌化 |
| 大标题导航栏 96 | 无令牌 | `02-advanced` §33、`09-layout` | 96 | ⚠️ 未令牌化 |

Tab 栏那条最要命：`09-layout` 的底部留白 82 = 58 + 8 + 16 依赖 58，而令牌是 56，按令牌取值会差 2pt。

**建议**：以 58 为准改令牌（贴合 iOS 26 悬浮 Tab 栏实际高度，且布局算式已建立在 58 上），并新增 `size.navbar-large = 96`、`semantic.*.scrim`。

#### B6. iOS 生成的字阶不随动态字体缩放

`iOS/Sources/WisdomUI/Foundation/WDTokenTypes.swift`：

```swift
public var font: Font { .system(size: size, weight: weight) }   // 固定字号，不随 Dynamic Type 缩放
```

`.system(size:)` 是固定尺寸，不跟随 Dynamic Type；Android 生成的是 `34.sp` / `17.sp`，`sp` 天然跟随 `fontScale`。于是「AX3 不截断 / fontScale 1.3 不截断」这条硬门槛在 iOS 上**结构性地不可能满足**，`lineSpacing = lineHeight - size` 也会跟着错。

**建议**：生成 `Font.custom("", size: size, relativeTo: .body)`（空名回落到系统字）；行高改用相对倍数；控件高度用 `@ScaledMetric`。必须在 M0 修，因为它是 Foundation 层，后面 36 个组件全部依赖。

#### B7. `docs/03-platform-mapping.md` 需整体重写

这份文档是开发者真正会照着写的上手页，而它通篇是 v0.2 之前的内容：

- 品牌色还是绿色系（`#2F7F63` / `#E0F0E8` / canvas `#F5F8F6`），与温和蓝无关；
- 命名是 `WdColor` / `WdRadius` / `WdSpace` / `WdTheme` / `WisdomTheme`，与 `04-architecture` 和两端仓库的 `WD*` 前缀、`WDTheme` 冲突；
- 路径是 `ios/Sources/...` 与 `android/wisdom-ui/src/main/java/com/wisdom/ui/`，实际是 `iOS/Sources/WisdomUI/` 与 `io.github.wlunc.wisdom`；
- 引用的 `color.brand.600` 这类令牌在当前令牌文件里根本不存在（脚本审计已确认）。

**建议**：按 v1.0 重写，或删掉正文只保留指向 `04-architecture` 与生成产物的指针。

#### B8. 游离数值破坏了「组件只用令牌」这条纪律

抽查发现的、既不在令牌里、也不在字阶 / 尺寸阶梯里的值：

| 位置 | 值 | 问题 |
| --- | --- | --- |
| `02-advanced` §34 TabBar | 图标 22、标签 10 · 500 | 图标阶梯只有 16/20/24/28；字号阶梯最小 11 |
| `02-advanced` §33 NavigationBar | 大标题区 52、总高 96 | 未令牌化 |
| `specs/01` 多处 | 1pt 描边、1.5pt 控件描边、2.2pt 勾、3pt 聚焦光环、40% 禁用不透明度 | 全是字面量 |
| `01-foundation` §3.6 | `--wash` 三个径向渐变 | 只存在于 CSS，无令牌、无深色版本 |
| `01-foundation` §7.2 | 玻璃 62% / 82% | 与 `material.*` 的 54/70/86 对不上 |

**建议**：新增 `component.*` 常量命名空间（描边宽度、聚焦环、禁用透明度、遮罩、勾线宽、Tab 图标尺寸…），以及 `gradient.wash.light / dark`。否则「组件代码里不允许出现字面量」这条规则从第一天就守不住，两端还会各自挑一个「看起来差不多」的值。

### 1.5 建议项（不阻塞，但强烈建议）

**S1. 把画廊的 `--g-*` 变成生成产物。** 现在画廊开头 35 个变量是手工照抄令牌（`05-preview` 明说「直接照抄」），这就是漂移的根因。让 `build.js` 顺手吐一份 CSS 变量块并纳入 `--check`，三类漂移一次性消失。

**S2. 给对比度加断言测试。** 两端各写一个单元测试，把「语义色 × 使用背景」列成表，跑 WCAG 公式断言阈值。B1–B4 全部能在 CI 里自动拦住，而不是靠人复算。

**S3. 三个仓库都要有 CI。** 至少：令牌生成一致性（`--check`）、两端编译、对比度断言、大字号截图回归。

**S4. 明确「配方不承诺兼容性」的边界。** 这个决定很好，建议补一句：配方只进业务仓库，不进组件库；只有满足三条提升标准的才进 `wisdom-ui` / `WisdomUI`。否则半年后场景配方会从业务代码反向污染组件库 API。

**S5. 文字缩放后的行高改成倍数。** 固定 `lineHeight` 在大字号下会挤压；改成 `size × ratio`，并把 ratio 放进令牌。

**S6. 中文字体不要嵌入。** `01-foundation` §4.1 提到 MiSans / HarmonyOS Sans SC：整套中文字体 9MB 起步，放进组件库等于强制每个宿主 App 付体积代价。建议只做字重映射，需要圆体时用系统 rounded 或按需子集化。

**S7. 组件规格的触控热区补一句平台差异。** `specs/*` 的验收项统一写「≥ 44×44」，而 `06-accessibility` 已说明「44 是 iOS 下限、Android 走 48dp」。建议规格里直接写「iOS ≥44 / Android ≥48」，免得照规格验收的人漏掉。

### 1.6 设计口味层面的建议（可讨论）

**T1. 浅色版主按钮的「主操作感」偏弱。** 按钮填充 `#8FCFDD → #63BAD2`，页面底是湖蓝 / 天青色晕 + 白卡。对比度完全达标，但它和背景同属一个明度带，`filled` 与 `tonal` 的差别主要靠色相旋转，一屏里找「该点哪个」会多花半秒。建议二选一：给 `filled` 补一层 1px 内高光；或让 `filled` 终点再深一档（如 `#4FB0C8`，配 `#0E3A55` 仍有 4.5:1 以上余量），其它组件不动。README 里「浅底深字的对比度其实比深底白字更高」是对的，但对比度达标 ≠ 视觉权重够。

**T2. Android 别追 Liquid Glass 的背景模糊。** `03-platform-mapping` 推荐引入 Haze，我的建议相反：Material 3 Expressive 自己的做法是色调与高度，不是实时模糊；实时模糊在中低端机上是持续的 GPU 开销，也是耗电项。把玻璃抽象成 `WDGlass` 策略，Android 默认走「近实底 + 顶部高光 + hairline」的降级实现（现成配方已有），Haze 作为可选依赖由宿主决定。这样设计系统的第三方依赖是零。

**T3. `caption2`(11) 就是绝对下限。** Tab 栏标签用 10pt 低于自定下限，中文 10pt 在低密度屏上会明显糊。建议 Tab 标签统一 `caption2` 11 · 500，靠字重而不是再降字号来区分层级。

**T4. 深色版是「深蓝」而不是「暗」。** `#0A1B2A` + `#14283A` 表面在深色下偏蓝，与浅色版的青灰调性不同温，观感会更「夜航」。如果这不是有意为之，建议把深色 canvas 往青灰压一点（朝 `su.900 #0A1B24` 靠），两端观感更连续。

**T5. `material.sheen` 的 3800ms 高光只留给 Hero 卡与空状态。** 它现在同时出现在材质表和卡片能力里，与「卡片不叠玻璃」的规则冲突；长时间循环扫光也是耗电与「闪」的来源。

### 1.7 两端实施计划

#### 1.7.1 排期原则

- **规格是契约，代码是两份实现**：每个组件先改 `docs/specs`，再两端同 PR 落地，验收清单逐条勾。
- **令牌先行**：缺的数值先进 `tokens/wisdom.tokens.json`，由 `build.js` 生成，组件里不出现字面量。
- **Foundation 先于组件**：玻璃降级、字体缩放、触觉、聚焦环这四件事必须在 M0/M1 冻结，否则每个组件都要返工一遍。

### 2.2 我完全认同的（不再复述理由）

B1 / B2 / B3 / B4 / B5 / B7 / B8 / B9 全部照做。其中三条特别值得强调：

| 条目 | 为什么重要 |
| --- | --- |
| **B6 iOS 字阶不缩放** | 这是 Foundation 层的结构性缺陷。后面 37 个组件的字号全部经过它，M2 之后才发现要全部返工。属于「现在花一天、以后花两周」的问题 |

### 2.3 修正一：T1 的解法方向反了，会推翻已确认的决定

架构师的判断是「浅色版主按钮主操作感偏弱」，建议是「让 `filled` 终点再深一档（如 `#4FB0C8`）」。

**但按钮的深度是上一轮明确调整过的**：用户看到深色填充后提出「按钮太深了，回调一下」，填充才从 `#1677B3` 回调到现在的 `#8FCFDD → #63BAD2`。照建议改，等于把刚否掉的方向再做一遍。

> **架构师**：`filled` 与 `tonal` 差别弱，建议把 `filled` 终点再深一档。
> **设计师**：诊断我接，但根因判断要修正。差别弱不是因为 `filled` 太浅，而是因为 **`tonal` 太像 `filled`**——

| 变体 | 当前填充 | 明度带 |
| --- | --- | --- |
| `filled` | `gradient.fill`（`#8FCFDD → #63BAD2`） | 浅 |
| `tonal` | `gradient.surface`（`#B0D5DF → #7EC4CF`） | 浅 |

两者在同一明度带上，只靠色相旋转区分。

**建议的解法：降 `tonal`，不加深 `filled`。**

1. `tonal` 改用 `gradient.tint`（品牌色 20% 透明叠加），或直接改为描边样式
2. `filled` 保持现有浅度，把 `elevation.brand` 投影与顶部 1pt 内高光加强

这样「浅」保住了，主次靠**形状与层次**拉开，而不是靠明度。用户不会觉得按钮又变深。

> **设计师**：架构师自己也写了「对比度达标 ≠ 视觉权重够」——这句是对的，我的修正只是换一条达到视觉权重的路径。
> **研发Leader**：我复核后确认这条成立（详见 §3）。

### 2.4 修正二：B6 诊断对，药方需要先验证

架构师建议 `Font.custom("", size: size, relativeTo: .body)`。**空字符串字体名依赖未文档化的回落行为**，能否稳定取到系统字需要先验证，不宜直接写进 Foundation。

两个更可靠的写法：

```swift
// 方案一：@ScaledMetric，语义最清晰，控件高度也能一起管
@ScaledMetric(relativeTo: .body) private var size: CGFloat = 17
Font.system(size: size, weight: .semibold)

// 方案二：显式按 text style 缩放，等价于 UIKit 的 UIFontMetrics
Font.system(
    size: UIFontMetrics(forTextStyle: .body).scaledValue(for: 17),
    weight: .semibold
)
```

**建议 M0 增加一个 0.5 天的预研**：把三种写法（`.custom("")` / `@ScaledMetric` / `UIFontMetrics`）在 AX1–AX3 下的实际渲染尺寸打印出来，再定 Foundation 的写法。Foundation 一旦冻结，后面全部组件依赖它。

> **研发Leader**：诊断对，但出口产物要更硬——不是一份对比报告，而是一个**冻结的 `WDTextStyle` 形态 + 生成器改动 + 一段打印实际行高的度量测试**。另外还有一层问题：行高公式本身也错了，见 §3.3。

### 2.5 修正三：M0 工期与范围要扩

理由：RTL 与命名方向、iOS 字阶预研这两项都是**命名 / 地基决策**，冻结后改动成本倍增，必须并进 M0。

| 项 | 原计划 | 修订 | 理由 |
| --- | --- | --- | --- |
| M0 工期 | 0.5–1 周 | **1.5 周** | 见 §2.8 的工作量拆解 |
| M0 范围 | 修 B1–B9 | **加 RTL 与命名方向 + iOS 字阶预研** | 两项都是命名/地基决策，冻结后改动成本倍增 |
| T1 处理 | 加深 `filled` | **降低 `tonal`** | 避免推翻已确认的决定 |
| B4 取值 | `#3FA0BC`（3.01） | **`#3898B4`（3.32）** | 留余量 |
| M6 描述 | 场景组件 7 项 | **1 个组件 + 5 个配方** | 配方不进库 |
| T4 深色偏蓝 | 建议改青灰 | **暂不动** | 深色版是用户明确「暂定」过的状态；等 M1 双端并排评审时再定 |
| S3 CI | 随 M0 一起建 | **对比度断言进 M0，其余门禁随 M1** | 对比度断言验证的是设计令牌本身；编译/API 冻结属于工程侧，用户当前重心在设计文档 |

### 2.6 我验证过、确认架构师是对的

**B2 的替代路线：我原本想提一条更省事的方案——不改文字色，改浅底色。复算后否掉了。**

| 项 | 数值 |
| --- | --- |
| 危险色 `#B8564D` 要达到 4.5:1，底色亮度需 ≥ | **0.957** |
| 纯白的亮度 | 1.000 |
| 当前软底 `#FBE7E4` 的亮度 | 0.833 |

底色要提到 0.957 几乎就是纯白，`status-soft` 会彻底失去颜色。**所以 B2 只能靠加深文字，架构师的方案是对的，新增 `status-text.*` 四个令牌照做。**

**B4：我本想反驳，复核后确认架构师是对的。**

我的第一反应是「勾不是唯一信号，未选与已选的差别还有底色」，据此可以算作不违规。按 WCAG 1.4.11 重推一遍后否掉了自己：

- 若底色变化是唯一区分手段，就违反 1.4.1（不能只靠颜色）
- 既然勾承担了区分职责，它就是「理解状态所必需的图形」，必须满足 3:1

**结论：`gradient.mid` 起点改为 `#3898B4`（3.32:1）**——架构师给的 `#3FA0BC` 是 3.01，刚过线，选余量更大的那个。

### 2.7 架构师漏掉的四点

#### 2.7.1 多语言与 RTL 完全没有覆盖（最要紧）

这是我认为最该补的一条，因为它是**命名决策**，冻结后再改等于全局重命名。

| 受影响处 | 问题 | 处理 |
| --- | --- | --- |
| 间距命名 | `09-layout` 通篇写「左右边距」 | 必须改为 leading / trailing |
| 图标 | `08-icons` 43 条对照表 | 新增「是否镜像」一列：`chevron.right` / `chevron.left`、`arrow.uturn.*`、`list.bullet` 需要镜像 |
| 文本对齐 | 规格里多处写「左对齐」 | 改为「起始边对齐」 |
| 进度与方向 | 环的起点、滑块的填充方向 | 环起点改为「起始边」，滑块在 RTL 下从右往左填充 |
| 卡片与列表 | 选中态的左侧色条 | 改为起始边色条 |

**建议进 M0**，与 B8 的 `component.*` 命名空间一起做——两件事都动命名，分两次做等于改两遍。

#### 2.7.2 两份验收清单会各自漂移

`06-accessibility` §10 有 16 条通用验收；37 个组件规格里每个又各有一套无障碍验收项。两者在触控热区、对比度、读屏标签上重叠。这与 B5 是**同一类「单一真源」问题**，只是发生在文档层而不是令牌层，所以架构师没列进 B5。

**建议**：组件规格的无障碍验收项只保留**差异项**（如「Steps 的边界禁用」「SearchField 的取消按钮展开」），通用项统一引用 `06-accessibility` §10。这样改通用规则只需改一处。

#### 2.7.3 S1 只解决了画廊漂移的一半

把 `--g-*` 改成生成产物是对的，但画廊更大的维护成本在于**组件标记是手写的**：每加一个组件要写三份（规格 + 画廊 HTML + 两端代码）。

**建议明确画廊的定位**：它是**阶段性评审产物，不承诺实时同步**——每次一批组件定稿时重生成一次，中间允许滞后。否则维护成本会随组件数线性增长，到 50 个组件时没人会去更新画廊。

#### 2.7.4 B9-4 不只是文档矛盾，它已经影响到计划本身

`04-architecture` §2 把 7 个场景项都列为「场景组件」，架构师的风险表也因此写了「组件数量与人力不匹配（43 项）」。实际口径是 **37 个组件 + 5 个配方**。这不是纯粹的文字问题——架构师的 M6 只列了 AssigneePicker 一个组件，说明他察觉到了，但没有把这条归进 B9。

**建议**：B9-4 的修复要连带修正 `04-architecture` §2 的分层表、§7 的 M6 描述，以及审阅自身的 43 项口径。

## 3. 研发Leader：移动端复核与补充

> 发言要点：架构师的 B1–B9 与设计师的三处修正**都成立**，可以据此开工；但正文三级色 `text.tertiary` 是一个被附录降级处理的真·阻塞项，且整套对比度账目都建立在「平铺底色」这个不成立的假设上——这两条要并进 M0。

### 3.1 复核方法

不重复架构师的审阅动作，只做三件事：

| 复核项 | 方法 | 结果 |
| --- | --- | --- |
| 对比度 | 按 WCAG 2.1 相对亮度公式独立复算附录 A 的 27 组数值 | **27/27 全部吻合** |
| 替代色值 | 复算 `status-text.*` 四个候选值与 `gradient.mid` 两个候选值 | **6/6 精确吻合** |
| 结构性指控 B5–B9 | 直接读令牌文件、规格、布局文档、画廊 HTML 与两端源码逐条核对 | **全部成立** |
| 令牌流水线 | `node tools/token-build/build.js --check` | **通过（退出码 0）** |
| 附带验证 | 检验「页面色晕」对文字对比度的影响（架构师与设计师都没做） | **发现新阻塞项，见 §3.2** |

**结论：两份文档的可信度都很高，可以按它们的判断开工。** 下面只写它们没写到的、以及我作为移动端实现方的补充。

### 3.2 新增阻塞项 B10：正文三级色不达标，且被色晕进一步拉低

`semantic.light.text.tertiary`（`#5B7784`）实测不达 `06-accessibility` §2 的 4.5:1 底线：

| 文字色 | 背景 | 文档声称 | 实测 | 判定 |
| --- | --- | --- | --- | --- |
| `text.tertiary` `#5B7784` | `bg.canvas` `#F1F8FA` | `06` §5.1 写 **4.7:1** | **4.43:1** | ❌ 低于 4.5 底线 |
| `text.tertiary` | 页面色晕左上合成色 `#C6E1E8` | — | **3.47:1** | ❌ |
| `text.tertiary` | 页面色晕右上合成色 `#BCE0E6` | — | **3.38:1** | ❌ |

架构师在附录 A 里把它标成「⚠️」，没有列进 B 清单；`06` §5.1 的验收表却写着「4.7:1」。这不是次要发现：

- 它实际用在**输入框占位符、Tab 栏未选中标签、时间戳、次要图标**上，全是真实文字；WCAG 1.4.3 对占位符同样适用。
- 结论与 B2 一致：只能靠**加深文字**解决，不能靠提亮底色（底色提到 0.95 亮度≈纯白，会失去颜色）。

> **研发Leader**：建议升为 **B10，进 M0**。把 `text.tertiary` 至少压到在 canvas 上 ≥ 4.5，并同步把 `06` §5.1 的声称值改成实测值。
> **设计师**：同意升 B10，取值并入 B1–B4 一批做——都动语义色，分两次做等于改两遍。

### 3.3 系统性风险：整套对比度账目建立在不成立的背景假设上

这是我认为比 B10 更值得提醒的一条。所有声称值都是拿**平铺的 `bg.canvas`** 算的，但 `01-foundation` §3.6 明确「页面不用纯色铺底」，真实页面底是那层 `--wash` 径向色晕（湖水蓝 66% + 天青 46% + 群青 18%）。把色晕合成到 canvas 上再算一遍：

| 文字 | 平铺 `bg.canvas` | 色晕左上（湖水蓝） | 色晕右上（天青） | 色晕底部（群青） |
| --- | --- | --- | --- | --- |
| `text.primary` `#0A1B24` | 16.36:1 | 12.83:1 | **12.50:1 ✅ 最不利** | 13.55:1 |
| `text.secondary` `#3E5764` | 7.10:1 | 5.57:1 | **5.43:1 ✅ 最不利**（余量很薄） | 5.88:1 |
| `text.tertiary` `#5B7784` | 4.43:1 | 3.47:1 | **3.38:1 ❌ 最不利** | 3.67:1 |

> **列标订正（见 §7.1）**：原表把 `5.43` 标在「色晕左上」，实际 `5.43` 属于**天青（右上）**档，左上（湖水蓝）是 `5.57`；三色标的最不利值统一落在**右上**档。§6.5 里的 `5.57`（66%）与本节并不矛盾——只是两个不同色标。

两个衍生问题：

1. **`--wash` 完全不在令牌里**（只存在于 CSS/HTML），没有深色版本。架构师的 B8 只提了一句。
2. **对比度断言不能只比两个 hex。** 语义色里有大量 alpha（`surface.card` 是 `#FFFFFFF0`、`surface.glass` 是 `#FFFFFFB3`、`text` 色系则在色晕上），必须支持「前景 alpha 合成到指定背景」。

**建议（进 M0）**：

- 把 `wash` 收进令牌，并给深色版本；
- 对比度断言支持 alpha 合成，并对每个语义色对**显式声明最不利背景**（canvas / 色晕左上 / status-soft / 卡片实底 / 玻璃）；
- 断言表里补上「色晕上的正文」这一组，否则 CI 会绿着，真机上页面顶部就能看到灰字糊掉。

### 3.4 iOS 字阶：问题不只是「不缩放」，行高公式本身也错了

架构师的 B6 与设计师的 §2.4 都聚焦「`.system(size:)` 不跟随 Dynamic Type」，方向正确。但 `iOS/Sources/WisdomUI/Foundation/WDTokenTypes.swift` 里还有一层更隐蔽的问题。

#### 3.4.1 `lineSpacing = lineHeight − size` 语义错了

SwiftUI 的 `lineSpacing` 是**在字体天然行高之上追加的额外行距**，而「字体天然行高 ≠ 字号」。以 body 为例：

| 项 | 值 |
| --- | --- |
| 设计行高 | 22 |
| SF Pro 17pt 天然行高 | ≈ 20.3 |
| 正确追加量 | ≈ 22 − 20.3 ≈ **1.7** |
| 当前实现 | 22 − 17 = **5** → 实际行框 ≈ 25.3，每行比设计松约 15% |

Compose 端 `TextStyle(lineHeight = 22.sp)` 是**总行框**，且 `includeFontPadding` 默认 `true` 还会再撑大。**两端一个偏松、一个更松，方向还不一样**——这正好解释了两端「视觉重量漂移」，但它其实是行高模型不一致造成的物理差，不是审美差。

#### 3.4.2 静态 `font` 结构上不可能缩放

`@ScaledMetric` 是 View 环境的属性，塞不进 `enum` 的静态常量。所以设计师的两条药方对，但**调用点形态要变**：

```swift
// 现在（结构上无法缩放）
Text(x).font(WDType.headline.font)

// 建议（ViewModifier 内部持 @ScaledMetric）
Text(x).wdFont(WDType.headline)
```

同时令牌生成器要额外吐**行高比 `lineHeight / size`**，而不是只吐 `lineHeight`。

**建议（进 M0）**：B6 的「0.5 天预研」出口不是一份对比报告，而是**一个冻结的 `WDTextStyle` 形态 + 生成器改动 + 一段打印实际行高的度量测试**。这是 M0 里最该冻结的 API 形态，因为 37 个组件全部经过它。

### 3.5 工程侧建议（按优先级）

#### 3.5.1 无障碍文案必须可注入，不能硬编码中文

`06` §3.2 的句式（「已完成 3 项，共 5 项」「家庭成员 6 人：…」）现在写死在规格里，但 `WisdomUI` / `wisdom-ui` 是会被别的 App 引入的库——库不能替宿主决定语言。组件 API 要留出文案插槽 / formatter，规格里的句子只作示例 App 的默认值。这同时是本地化与 RTL 的前提。

#### 3.5.2 令牌变更会撞 `apiCheck`，流程要固定

Android 已开 `explicitApi()` + `binary-compatibility-validator`，`apiCheck` 挂在 `:wisdom-ui:build` 上。M0 加 `status-text.*`、`component.*`、`wash`、改 `WDTextStyle` 都会改公开面，流程要固定为**「改 JSON → 生成 → `apiDump` → 提交」**，否则每个 PR 都红。iOS 侧 `swift-api-digester` 不是 SPM 现成命令，别把「冻结公开 API」写进 M0 出口，那属于 M3。

#### 3.5.3 RTL 落地要连画廊一起验

命名冻结在 M0 对，但画廊 HTML 里有 **12 处 `left` / 16 处 `right`** 硬编码；列表选中态是「左侧 3pt 色条」；Divider 内缩 62；`chevron.right` 需镜像。建议 M1 的截图基线里加一条 `dir="rtl"` 渲染，否则「浅/深 × AX3 × LTR/RTL 六态」里那张 RTL 图是假的。

#### 3.5.4 把派生布局常量也令牌化

B8 的 `component.*` 建议顺带收进：Tab 栏底留白 **82**、FAB 有 Tab 时偏移 **92**、Divider 内缩 **62**、遮罩、勾线宽、聚焦环。现在 82 / 92 / 62 只活在文档算式里，两端一定会各挑一个「差不多」的数。

#### 3.5.5 小账（已复核，均为真）

| 项 | 现状 | 建议 |
| --- | --- | --- |
| 色卡数量 | README 与 `01` §3.1 写「十二个色」，`color.named` 实际 **9 个** | 改成 9，或补齐到 12 |
| Tab 栏高度 | 令牌 `size.tabbar-height` **56** vs `02` §34 / `09` **58** | 按 58 改令牌（底部留白 82 的算式建立在 58 上） |
| 玻璃透明度 | `01` §7.2 写「导航 62% / Tab 62% / 浮层 82%」，`material.*` 实际是 **54 / 70 / 86%** | 三个数统一到令牌 |
| `navbar-large` / `scrim` / `component.*` | 令牌里均不存在 | 与 B8 一批新增 |

### 3.6 对计划的微调

设计师 §2.8 的 M0 = 1.5 周、合计 12–13 周我基本认同，只改三点：

| 项 | 原计划 | 我的修订 |
| --- | --- | --- |
| M0 出口条件 | `--check` + 对比度断言 + 两端编译 | **加两条**：(a) 对比度断言支持 alpha 合成 + 每个色对声明最不利背景；(b) 冻结 `WDTextStyle` 形态与生成器（行高比） |

| B10 与 wash | — | **并进 M0**，和 B1–B4 一批做——都动语义色，分两次做等于改两遍 |

优先级上，M0 里最不能出错的是**「字阶 / 行高模型」**和**「语义色（含 tertiary）」**，因为 M2 之后所有组件都压在它们上面，返工成本最高。

3. **按修订后的 M0 开工**：`改令牌 → apiDump → 改规格 → 改文档 → 重生成 → 两端编译 + 断言`，每步跑一次验证；
4. **M0 收尾冻结命名（含 RTL）**，再开 M1 Foundation——这一步冻结之后，后面 36 个组件才不会再动地基。

## 6. 设计师（第二轮）：对研发Leader意见的回应

### 6.1 复核：两条新指控成立，且性质比 B9 严重

不重复它的审阅动作，只复算它给出的新数字：

| 指控 | 它的数值 | 我的复算 | 结果 |
| --- | --- | --- | --- |
| 色晕左上（湖水蓝 66%）合成色 | `#C6E1E8` | `#C6E1E8` | 吻合 |
| `text.tertiary` on `bg.canvas` | 4.43:1 | 4.43:1 | 吻合 |
| `text.tertiary` on 色晕左上 | 3.47:1 | 3.47:1 | 吻合 |

**性质判断：这两条比 B9 那七条严重。** B9 是"文档没跟上改动"，改文字即可；B10 与 §3.3 是**语义色本身的定义错了**——

- `text.tertiary` 是我定的，我在 [06 §5.1](06-accessibility.md) 里声称它 4.7:1，实际 4.43，**连自己的验收表都没过**；
- 更根本的是 §3.3：我所有对比度都是拿**平铺的 `bg.canvas`** 算的，而 [01 §3.6](01-foundation.md) 明写"页面不用纯色铺底"。**我用自己定的规则否定了自己的账目。**

研发Leader 那句"断言不能只比两个 hex"是这两条的正解，已并入 [§4.2](#42-m0-出口条件三方合并) 第 2 条。

### 6.2 裁定：`text.tertiary` 取 `#4C616D`（加深，不降级）

它的 §3.2 给了两个方向（加深 / 降级为图形专用色）。**选加深**，取值 `#4C616D`：

| 候选 | on `bg.canvas` | on 色晕左上 66% |
| --- | --- | --- |
| 现在 `#5B7784` | 4.43 ❌ | 3.47 ❌ |
| `#50656F` | 5.70 ✅ | 4.47 ❌ |
| **`#4C616D`（采纳）** | **6.04 ✅** | **4.74 ✅** |
| `#4A5F6B` | 6.22 ✅ | 4.88 ✅ |

**为什么不选 `#50656F`**：它在色晕上差 0.03。不能采纳一个"换个背景就不达标"的值——这与 B10 的成因是同一个错误。

**代价要说清**：`#4C616D` 与 `text.secondary #3E5764` 的对比度只差 1.18 倍（6.04 vs 7.10）。
也就是说**第三级的层级从"靠颜色"变成"靠字号 + 颜色共同承担"**（12 / 13 / 15 三档字号本来就在字阶里）。
这条要补进 [01 §4.3](01-foundation.md) 的字体规则，否则以后会有人继续用缩小字号来加层级。

同步动作：`06 §5.1` 的声称值改为实测值。

### 6.3 裁定：`tonal` 走 tint 叠加，不改描边

它在 §3 没展开，我在这里定形态。两个候选：

| 方案 | 效果 | 判定 |
| --- | --- | --- |
| **tint 叠加**（品牌色 18–22% 叠在卡片底上） | 保留"次级操作有底色"的语义 | ✅ 采纳 |
| 改成描边 | 与 `outline` 撞车——两者都变成"无底 + 边" | ❌ |

采纳 tint 的关键理由不是形态，而是**亮度阶梯**：

| 层 | 填充 | 相对亮度 |
| --- | --- | --- |
| `filled` | `gradient.fill`（`#8FCFDD → #63BAD2`） | ≈ 0.56 |
| **`tonal`（新）** | tint ≈ `#D5EBF6` | **≈ 0.80** |
| 页面底 | `bg.canvas` `#F1F8FA` | ≈ 0.93 |

三级拉开且单调，主次靠**明度**而不是色相旋转。同时 `text.on-soft #123F5C` 在 tint 上是 9.72:1，余量充足。

这样处理**不改变 `filled` 的浅度**，因此不推翻此前"按钮太深了，回调一下"的决定——这正是 [§2.3](#23-修正一t1-的解法方向反了会推翻已确认的决定) 主张的解法。

新增令牌：`semantic.*.gradient.tint`（当前只有 `material.tinted` 里内联的一个值，属 B8 的游离值）。

### 6.4 §4.5 第 4 项：中文字体不嵌入（设计侧立场）

设计侧明确建议**不嵌入**：整套中文字体 9MB 起步，放进组件库等于强制每个宿主 App 付体积代价。
只做字重映射；需要圆体时用系统 rounded（iOS）或按需子集化。

> 这条仍需用户确认，因为"家庭感"是否值得这点体积是一个产品取舍，不是纯设计判断。

### 6.5 新增设计决策：色晕浓度 66% → 42%

这是我在本轮里最想推动的一处，理由是它同时解决两个问题。

| 湖水蓝浓度 | 合成色 | `text.secondary` | `text.tertiary #4C616D` |
| --- | --- | --- | --- |
| 66%（现在） | `#C6E1E8` | 5.57 | 4.74 |
| 55% | `#CDE5EB` | 5.81 | 4.94 |
| **42%（采纳）** | **`#D6E9EF`** | **6.09** | **5.18** |
| 35% | `#DAECF1` | 6.27 | 5.33 |

1. **达标需要**：色晕是文字的直接背景，66% 太浓，让所有前景色的余量都变薄；
2. **顺应用户诉求**：用户前后三次提出"再浅一点"。降浓既让对比度更稳，又正好是这个方向。

配合 [§3.3](#33-系统性风险整套对比度账目建立在不成立的背景假设上)：`wash` 收进令牌、出深浅两版，并进 `--check`。

### 6.6 新增设计决策：令牌改存行高比，不存行高绝对值

[§3.4](#34-ios-字阶问题不只是不缩放行高公式本身也错了) 指出 `lineSpacing = lineHeight − size` 语义错误，成立。
但它暴露的是**设计交付物格式**的问题，不只是实现细节：

> 动态字体下，"22pt 行高"这个绝对量本身不成立——字号放大后行高必须等比放大。

所以设计侧真源改为：

```
type.body = { size: 17, lineHeightRatio: 1.29, weight: 400 }
```

行高绝对值（22）是 `size × ratio` 的派生值，只用于设计稿标注。平台适配层拿 ratio 后按各自字体实际行高换算。

这条列入 M0 冻结清单——**它是 37 个组件全部经过的地方，返工成本最高**。

### 6.7 新增设计决策：色卡就写 9 个，不补齐到 12

[§4.1](#41-最终阻塞项-b1b10合并清单) 的 B9 把"十二个色"列为文档矛盾。这不是笔误，是定稿时的收敛动作没同步到文档：

| 处理 | 色 |
| --- | --- |
| 用户原图里重复的 | 霁蓝 `#2A5CAA` 与景泰蓝同值，删一个 |
| 合并未使用的 | 品蓝 `#003D74`、宝蓝 `#1F286F` 退出色卡 |

12 − 1（重复）− 2（未使用）= **9**。建议文档改成 9 并注明这三处处理，而不是为了凑数把两个没人用的深蓝加回去——
**色卡应该反映系统实际在用的色，不是收藏夹。**

### 6.8 新增设计交付：文案的「契约 / 默认值」分界

[§3.5](#35-工程侧建议按优先级) 4.1 说"无障碍文案必须可注入"，成立。但它对设计文档的连带影响没说透：

[06 §3.2](06-accessibility.md) 的 20 条句式模板、[07](07-content.md) 的全部文案示例，**现在是以"契约"身份存在的**。
库要被别的 App 引入时，它们只能降格为默认值。设计文档需要划这条线：

| 是契约（必须遵守） | 是默认值（宿主可替换） |
| --- | --- |
| 必须包含数量与单位 | 用"已完成 3 项"还是"3 of 5 done" |
| 必须先说用途再说权限请求 | 权限文案的具体措辞 |
| 错误必须含"哪里错 + 怎么改" | 具体的那一句 |
| 危险操作必须说明后果 | 标题的具体问法 |

不划清这条线，以后每个接入方都会问"这句能不能改"，而文档给不出答案。

### 6.9 对 §4 共识的补充

三处补充，不改变 B1–B10 的清单：

1. **M0 冻结合并为一次变更**。要冻结的是四件：语义色（含 tertiary）、色晕令牌与浓度、`WDTextStyle` 形态 + 行高比、RTL 命名方向。前三件都改颜色或字号，**建议一次令牌变更 + 一次生成 + 一次 `apiDump`**；分三次做等于把 37 个规格和 3 个画廊各改三遍。
2. **[§4.2](#42-m0-出口条件三方合并) 出口条件补一条**：色卡数量与文档描述一致（B9 第 1 条），避免"改了一半"。
3. **RTL 的图标镜像要带判断，不是机械加列**：`chevron.*` / `arrow.uturn.*` / `list.bullet` 需要镜像，`clock` / `calendar` / `heart` / 播放暂停类不镜像。这条属 [08](08-icons.md) 的交付物，与命名冻结同批。

### 6.10 对 §3.5 工程侧建议的逐条回应

§3.5 里 4.1 已在 §6.8 回应，其余四条按设计视角逐条表态。

**4.2 令牌变更会撞 `apiCheck`，流程要固定 —— 同意，并补一条设计侧义务。**

流程固定为「改 JSON → 生成 → `apiDump` → 提交」之后，设计侧要额外提供一件东西：
**每次令牌变更给一份影响清单**（改了哪些语义令牌、影响哪几个组件）。否则实现方要自己去翻 37 份规格判断影响面。
建议由生成器顺带输出一份 `token-usage.md`——把每个语义令牌被哪些组件规格引用列出来。这是 [S1](#15-建议项不阻塞但强烈建议) 的自然延伸，不额外增加维护量。

**4.3 RTL 落地要连画廊一起验 —— 同意结论，但不建议把画廊改成逻辑属性。**

画廊是**设计稿**，不是产品代码。它的职责是让人看到镜像效果，而不是跟随浏览器方向。所以：

| 对象 | 处理 |
| --- | --- |
| 组件库的规格描述（01 / 09 / specs） | 改成 leading / trailing —— 这是命名契约 |
| 画廊 HTML | 保留实体方向属性，但在 M1 加一个 `dir="rtl"` 的**对照容器**渲染同一批组件，与 LTR 并排 |

这样评审时能直接看到"镜像之后对不对"，而不是靠脑补。它也正好符合画廊"浅深并排"的既有做法——**再并一列 RTL**。

**4.4 把派生布局常量也令牌化 —— 同意，但要区分「常量」和「派生值」。**

它列的 82 / 92 / 62 三个数里，其实只有一部分是真常量：

| 数 | 来源 | 处理 |
| --- | --- | --- |
| Tab 栏底留白 **82** | 58 + 8 + 16 | 派生值 |
| FAB 有 Tab 时偏移 **92** | 58 + 8 + 16 + 10 | 派生值 |
| Divider 内缩 **62** | 16 + 34 + 12 | 派生值 |

**这三个都是算式的结果，不是独立常量。** 如果按绝对值存进令牌，改一次列表图标底座（34 → 36）就会三处同时漂，而且没人知道该改哪。

建议：令牌里只存**组件参数**（行内距 16、图标底座 34、段间距 12、Tab 栏高 58、栏与底部间距 8），由生成器算出 82 / 92 / 62 并在生成产物里注释来源。这样改一个参数，三处自动跟着走。

**4.5 小账五项 —— 四条同意，玻璃那条设计侧要给一个裁决。**

| 项 | 设计侧表态 |
| --- | --- |
| 色卡数量 9 vs 12 | 见 §6.7，改文档为 9 |
| Tab 栏 56 vs 58 | **以 58 为准**，令牌改 58。58 是悬浮胶囊的视觉高度，且 82 的算式建立在它上面 |
| `navbar-large` / `scrim` / `component.*` 不存在 | 同意新增，并入 B8 |
| 玻璃透明度三个数打架 | 见下 |

玻璃这条比它列的更乱——**实际有三个数不一致**：

| 来源 | 数值 |
| --- | --- |
| [01 §7.2](01-foundation.md) 正文 | 导航 62% / Tab 62% / 浮层 82% |
| `material.*` 令牌 | ultraThin 38 / thin 54 / regular 70 / thick 86 |
| 画廊实际渲染 | 导航与 Tab 用 `--g-glass-strong` ≈ **88%** |

**设计侧裁决：以 `material.*` 令牌为准，并把 01 那句改成引用令牌名。**

| 用途 | 采用档位 | 理由 |
| --- | --- | --- |
| 导航栏、Tab 栏 | `material.regular` **70%** | 88% 太实，失去玻璃通透；54% 又太透，文字对比度不稳 |
| 浮层、Sheet 头 | `material.regular` 70% | 同上 |
| 模态、Toast | `material.thick` **86%** | 需要文字稳定可读 |
| 表头、输入浮层 | `material.ultraThin` 38% | 只做轻提示，下面有实底托着 |

画廊的 `--g-glass` 由 88% 改到 70%，与令牌对齐。

三点全部接受，其中两点影响 M0 的工期：

## 7. 研发Leader（第二轮）：对 §6 裁定的订正与补充

> 针对 [§6](#6-设计师第二轮对研发leader意见的回应) 的回应。
> 结论：**§6.2 / §6.3 / §6.6 / §6.7 四项裁定接受；但 §6.5 的色晕最不利取值需按三色标重取，色晕的「净 alpha」与深色版本仍是空白，玻璃裁决与 `06 §5.2` 冲突。另有四处工程侧落地细节。**

### 7.1 §6.2 / §6.5 数值复核：tertiary 采纳，色晕最不利取值订正

§6.2 的四个候选值逐个复算，**4/4 精确吻合**（`#5B7784` 4.43 / 3.47、`#50656F` 5.70 / 4.47、`#4C616D` 6.04 / 4.74、`#4A5F6B` 6.22 / 4.88），`#4C616D` 在 canvas 与色晕 66% 上均达标，**采纳**。

§6.5 的表格只按湖水蓝一个色标计算。色晕有三个色标，天青档更不利，按 **三色标取最不利** 重算：

| 色晕浓度 | 指标 | 仅湖水蓝（§6.5 口径） | 三色标取最不利（订正） |
| --- | --- | --- | --- |
| 66%（现行） | `text.secondary` | 5.57 | **5.43** |
| 66% | `text.tertiary` `#4C616D` | 4.74 | **4.61** |
| 42%（采纳） | `text.secondary` | 6.09 | **6.01** |
| 42% | `text.tertiary` `#4C616D` | 5.18 | **5.11** |

结论不变（42% 下 tertiary 仍有 5.11），但 §6.2 自己立的规矩——「不能采纳一个换个背景就不达标的值」——要一致地用在三个色标上。

**连带订正 §3.3 的列标**（已在原文修好）：该表把 `5.43` 填在「色晕左上」，实际 `5.43` 属于**天青（右上）**档，左上（湖水蓝）是 `5.57`。§3.3 与 §6.5 并非矛盾，是列标写错了。

### 7.2 色晕有两个互斥的定义，「最不利底色」取不准

- `01-foundation` §3.6 直接写 `rgba(176,213,223,.66)`；
- 预览 HTML 是 `color-mix(...#B0D5DF 66%...)` 再叠 `.wd-canvas-sheet::before { opacity:.55 }`，**净 alpha = 0.66 × 0.55 = 0.363**。

两者合成色差一整档：

| 口径 | 湖水蓝合成色 | 旧 tertiary `#5B7784` | 新 tertiary `#4C616D` |
| --- | --- | --- | --- |
| 文档 `.66` | `#C6E1E8` | 3.47 | 4.74 |
| 预览净 `.363` | `#D9EBF0` | 3.87 | 5.28 |

所以 §6.5「色晕收进令牌 + 进 `--check`」是必须的，且令牌里要写明**生效 alpha**，并说清预览那个 `.55` 元素透明度是否计入。否则断言测的与实现渲染的不是同一件事。

### 7.3 深色色晕未定义，且现况已超标

预览里 `--wd-wash` 是「两套主题共用一份定义」（硬编码浅色系，未用 `light-dark()`），`#wd-board.wd-dark` 只改了 `color-scheme`。于是深色模式下同一层浅蓝色晕罩在深色底上：

| 项 | 值 |
| --- | --- |
| 深色 canvas 叠上色晕（预览净 alpha） | `#465F6C` |
| `text.primary #E6F1F6` 其上 | 5.87 ✅ |
| `text.secondary #A4BCCB` 其上 | **3.42 ❌** |

且这已是用较弱的预览 alpha；若按文档 `.66` 会更糟。**§6.5 只定了浅色 42%，深色色晕的浓度与色值是空着的**——这不是增强项，是一个已成形的不达标。深色色晕须单独定义并进断言。

### 7.4 §6.3 两个数复算不出

| 项 | §6.3 写的 | 复算 | 说明 |
| --- | --- | --- | --- |
| `filled` 亮度 | ≈ 0.56 | `#8FCFDD`（渐变**起点**）0.557 | 0.56 是起点亮度；渐变中点 0.489、暗端 0.424。用起点作代表对「与 tint 拉开」是保守选择，但需注明取的是哪一点 |
| `text.on-soft #123F5C` 在 tint 上 | 9.72 | **9.01**（on `#D5EBF6`） | 需对齐是哪个 tint 值 / 底色 |

阶梯单调（0.56 / 0.80 / 0.93）与「主次靠明度」的结论不受影响。

### 7.5 玻璃裁决与 `06 §5.2` 冲突

§6.10 裁定导航栏、Tab 栏用 `material.regular` **70%**，但 `06` §5.2 的硬规则是「**文字必须落在 `glass-strong`（82%+）上，不用 ultraThin**」。导航标题与 Tab 标签都是文字，按新裁决落在 70% 上，**违反同一份规范**。两种调和方式，二选一：

1. 带文字的栏位改走 `material.thick`（86%）/ `surface.glass-strong`（85.9%），保留原规则；
2. 把 `06` §5.2 放宽为「≥70%，且该档位下的最不利合成色经断言验证」，并说明背景受控（色晕）时可用 `regular`。

### 7.6 工程侧落地细节（补 §3.5）

1. **iOS 行高比的落地要二选一并写进 `WDTextStyle`**：SwiftUI 的 `.lineSpacing` 无法锁定总行框，M0 冻结时须明确 (A) `lineSpacing = ratio × size − 实测天然行高(style, weight)`，或 (B) 走 `NSParagraphStyle.lineHeightMultiple / minimumLineHeight`。Compose 配 `LineHeightStyle` + `includeFontPadding = false`。另：`caption2` 的比值（13/11 = 1.18）是字阶里的离群值，需单独核。
2. **FAB 的 92 用公布参数拼不出来**：58 + 8 = 66，92 − 66 = 26，而 FAB 自身底部偏移是 18、内容内缩是 16；§6.10 写的「+10」无对应令牌。§6.10 4.4「按参数派生」方向正确，但它会先逼你看清 FAB 这条算式自身不自洽。
3. **文案默认值意味着公开 API 变更**：§6.8 的「宿主可替换」要求组件公开面接收文案 / 标签（一个 `WDLocalization` / formatter 类型）。这是 Foundation 层，属 M0，不能等逐个组件再加。
4. **「第三级靠字号承担」需给映射**：必须写明哪些字阶用 `text.secondary`、哪些用 `text.tertiary`。12 / 13 / 15 里 12 与 13 只差 1pt，不给映射这条无法验收。

### 7.7 并入决议

本轮订正并入 [§4](#4-三方共识最终阻塞清单与-m0-范围)，新增两条 M0「必须先定义」项与两行开放项：

- **M0 出口条件 +2**（见 [§4.2](#42-m0-出口条件三方合并) 第 7、8 条）：色晕令牌写清净 alpha 并出深色版本、经最不利断言；玻璃档位与 `06 §5.2` 调和。
- **开放项 +2**（见 [§4.5](#45-待裁定的开放项)）：深色色晕的浓度与色值；玻璃 70% vs `06 §5.2` 的 82%。

两项都不改变 M0 = 1.5 周的量级。

## 8. 架构师（第三轮）：复算、开放项裁决与三条结构建议

> 发言要点：§6.2 / §6.5 / §7.1 / §7.2 / §7.3 / §7.4 的**每一个数字我都独立复算过，全部吻合**，B10 的 `#4C616D` 可以定稿。但有四处需要补充：**§7.3 漏了深色端最严重的那一个数**；深色色晕是**有可验证解**的，不必挂在开放项里；「最不利底色」的取法要落成算法；玻璃档位与深色色晕其实是同一个问题。另有三条结构层建议，比单点修数更值钱。

### 8.1 复算结论：以下可以直接定稿

| 项 | 复核结果 |
| --- | --- |
| §6.2 四个候选值（含 66% 天青档） | **4/4 吻合**：`#5B7784` 4.43/3.47/3.38、`#50656F` 5.70/4.47/4.35、`#4C616D` **6.04/4.74/4.61**、`#4A5F6B` 6.22/4.88/4.76 |
| §6.5 42% 合成色 | 吻合：湖水蓝 `#D6E9EF`、天青（按比例 0.293）`#CFE9ED` |
| §7.1 三色标取最不利 | 吻合：66% secondary 5.43 / tertiary 4.61；42% secondary 6.01 / tertiary 5.11 |
| §7.2 净 alpha 口径 | 吻合：0.66 × 0.55 = 0.363 → `#D9EBF0` |
| §7.3 深色合成色 | 吻合：`#465F6C`，primary 5.87 / secondary 3.42 |
| §7.4 亮度与 tint 对比度 | 吻合：filled 起点 0.557 / 中点 0.490 / 暗端 0.424、canvas 0.927、tint 0.802、`#123F5C` on tint **9.01**（设计侧写的 9.72 确为笔误） |

**结论：B10 取 `#4C616D` 定稿。** 它在最严口径（色晕 66% 的天青档）下仍是 4.61，比次优候选 `#50656F` 的 4.35 更稳，且保留了「不采纳换个背景就不达标的值」这条自设规矩。

### 8.2 四条订正与补充

#### 8.2.1 深色端最严重的是 tertiary，不是 secondary（**2.40:1**）

§7.3 只测了 primary 与 secondary。把三级色一并算上：

| 文字 | 深色色晕现况 `#465F6C` | 判定 |
| --- | --- | --- |
| `text.primary` `#E6F1F6` | 5.87 | ✅ |
| `text.secondary` `#A4BCCB` | **3.42** | ❌ |
| `text.tertiary` `#839EB0` | **2.40** | ❌ 连 3:1 都不到，是本轮讨论里最低的一个数 |

Tab 栏未选中标签用的正是 `text.tertiary`，也就是说**深色模式下底栏文字现在处于最差的一档**。这条要写进 B10 的深色侧，和浅色侧一起修。

#### 8.2.2 深色色晕有可验证的解，不必留在开放项

深色端出现「浅蓝色晕罩暗底」的根因是 `--wd-wash` 硬编码了浅色色卡，且两套主题共用。**深色色晕应当由深色渐变族派生**——`semantic.dark.gradient.surface` 的两个色（`#123449` / `#0F4055`）本来就是为深色背景准备的：

| 方案 | 合成底 | primary | secondary | tertiary |
| --- | --- | --- | --- | --- |
| 现况（浅色卡叠深底，净 α .363） | `#465F6C` | 5.87 | 3.42 ❌ | 2.40 ❌ |
| **改由 `#123449` 36% 叠加** | `#0D2435` | **13.84** | **8.05** | **5.66** ✅ |

三个层级全部达标且余量充足，视觉上仍是「深色底 + 更深的蓝」，不会把深色页面抬亮。建议 §4.5 的「深色色晕的浓度与色值」从**待定义**变成**已给候选，M0 断言验证后定稿**。

#### 8.2.3 「最不利底色」要落成算法，不能手挑色标

§3.3 与 §7.3 两次手挑色标，一次对、一次漏（漏了 tertiary）。规律其实很明确：

| 外观 | 最不利合成色 | 为什么 |
| --- | --- | --- |
| 浅色 | 合成色**最深**的那个色标（天青 `#7EC4CF`） | 与深色文字明度差最小 |
| 深色 | 合成色**最亮**的那个色标（湖水蓝 `#B0D5DF`） | 与浅色文字明度差最小 |

方向相反，所以「取最不利」必须是断言里的规则，而不是人读表时的判断：**对色晕的每个色标 × 每个 alpha 档（含端点与中点）采样，自动取与文字明度差最小者**。

#### 8.2.4 B10 的加深是必须的，降浓度救不了它

| 旧 `#5B7784` | 66% 天青 | 42% 天青 |
| --- | --- | --- |
| 对比度 | 3.38 | **3.74**（仍 < 4.5） |

也就是说 §6.5 降浓度与 §6.2 加深是**两件都要做的事**，不能互相替代。这条要写进 M0 变更说明，免得以后有人拿「色晕已经降到 42%」当作不改三级色的理由。

### 8.3 两条开放项的裁决建议

#### 8.3.1 §4.5 第 6 项（玻璃 70% vs 82%）：第三个答案更好，而且它和第 5 项是同一个问题

实测（含 alpha 合成）：

| 档位与背景 | 合成底 | primary | secondary | tertiary |
| --- | --- | --- | --- | --- |
| 浅色 `glass` 70% 叠最不利色晕 | `#F1F8FA` | 16.36 | 7.10 | 6.04 ✅ |
| 深色 `glass` 54.9% 叠**现况**色晕（`#465F6C`） | `#253947` | 10.42 | 6.06 | **4.26 ❌** |
| 深色 `glass` 54.9% 叠**修正后**色晕（`#0D2435`） | `#0B1F2E` | 12.06 | 7.10 | **5.99 ✅** |

三点结论：

1. **浅色 70% 是安全的**，而且有个干净的巧合：70% 白叠最不利色晕后的合成色恰好是 `#F1F8FA`，与 `bg.canvas` 同值——**栏位文字只需按 canvas 那一组断言**，不必为玻璃单独开一套。
2. **深色端的问题来自色晕，不来自玻璃档位。** 先按 8.2.2 修深色色晕，现存的 54.9% 深色玻璃上 tertiary 就有 5.99，**玻璃档位不需要改**；反之若色晕不动，抬到 78% 也只有 5.10。
3. **`06 §5.2` 的「82%+」在深色端无解**：深色 `glass-strong` 只有 78%（`#0C1E2EC7`），规则本身写不成百分比。

建议 `06 §5.2` 改成结果式：

> 承载文字的栏位不得使用 `ultraThin`；文字对**最不利合成背景** ≥ 4.5:1（含 alpha 合成与色晕采样）；浅色档取 `material.regular`（70%），深色档取 `material.glass` 及以上且必须绑定修正后的深色色晕；验收取最不利位置，不取平均。

连带：`01 §7.2` 的「导航 62% / Tab 62% / 浮层 82%」删掉，改为引用令牌名；`02 §34` 的 Tab 未选中标签在深色下必须落在达标档位之上。

#### 8.3.2 §6.3 的 tint 值复算不出配方

按「品牌色 18–22% 叠底」复算：

| 配方 | 结果 | `#123F5C` 其上 |
| --- | --- | --- |
| 品牌 18% 叠白 | `#D5E7F1` | 8.74 |
| 品牌 20% 叠白 | `#D0E4F0` | 8.48 |
| 品牌 22% 叠白 | `#CCE1EE` | 8.23 |
| **设计稿给的 `#D5EBF6`** | — | 9.01 |

`#D5EBF6` 不对应任何一档配方。建议令牌只存**配方 + 基准底**（并且要写明基准底是 `surface.card` 还是 `bg.canvas`——叠白与叠 canvas 差一档），hex 由生成器算。否则又是一个结构上「值算不出来」的账。

#### 8.3.3 §6.3 的根因可以再 sharp 一点（不影响裁定）

`tonal` 读不出「按钮」，不只是明度带重叠，而是它**直接复用了 `semantic.*.gradient.surface`，而这个令牌的语义就是「背景层」**。用背景层的令牌做组件底，天然会被读成「没有底」。

实测三档明度：`filled` 0.557 → 0.424，`tonal`（现）0.621 → 0.484，两者在 **0.484–0.557 区间重叠**；改 tint 后为 0.802，与 canvas 0.927 之间留出 0.24 的空档，阶梯单调。改完 `gradient.surface` 只剩「图标底座 / 背景层」一个消费者，正好回到它的定义。

### 8.4 三条结构建议

#### 8.4.1 把「账目」变成生成物——本次讨论最该沉淀的一条

三轮讨论暴露了三类漂移（令牌↔规格、令牌↔画廊、规格↔规格），每一类都是靠人工复算才发现的。根因是**同一个数值在四处被记录**：`01 §3.1`（色卡对比度）、`06 §5.1`（语义色声称值）、`05`（画廊色值）、生成产物。

建议立一条原则：**数值只允许存在于令牌一处，其余文档只写规则、不写数值**，需要的表格一律由生成器产出：

```text
tokens/contrast.json          显式声明：前景 × 背景 × 场景（canvas / 色晕最不利 /
                              status-soft / 卡片实底 / 玻璃 / 照片）× 阈值 × 是否允许 alpha
tools/token-build/build.js    断言全部配对（支持 alpha 合成 + 渐变采样）
                              └→ 输出 docs/contrast-report.md
01 §3.1 / 06 §5.1             表格改为引用 contrast-report.md，不再手写数字
```

同一条原则下的既有建议：画廊 `--g-*` 改为生成（S1）、`token-usage.md`（设计侧 §6.10 已提）。再加一条——**「组件里不写字面量」用 lint 守住**：两端各一条规则（SwiftLint 自定义 / ktlint + detekt），命中 `Color(0x`、裸 hex、裸数值即构建失败，白名单显式列出。B8 才会从「文档里的纪律」变成「构建会红」。

#### 8.4.2 M0 的「冻结 `WDTextStyle`」应降级为「定形态 + M1 出结论」

§7.6.1 已经指出 iOS 侧还要在 `.lineSpacing` 换算与 `NSParagraphStyle` 之间二选一，而「总行框 = ratio × size」哪条能达成必须实测。**在纸上冻结一个没验证的 API 形态，正是这轮讨论反复在纠正的那类错误。**

建议 M0 出口写「形态冻结 + 预研记录」，把「确认冻结」挪到 M1 出口（M1 本来就有两端 Showcase 六态截图，正好是验证点）。

同理 M0 的范围：现在装了 10 项阻塞 + 4 项地基决策 + 生成器 + 断言框架 + 文档重写 + 两端 lint / 断言接入。设计侧自估 6 天**只算了设计侧**，两端实现方还要跟着改生成器、断言与 lint。建议 M0 明确只交付「改令牌 + 生成器 + 断言 + 文档」，**两端接入与 `WDTextStyle` 落地放 M1**；否则 1.5 周会以「冻结」为名压缩掉验证时间。

#### 8.4.3 「第三级靠字号承担」需要一张映射表才可验收（接 §7.6.4）

| 语义 | 色 | 字阶 | 例 |
| --- | --- | --- | --- |
| 主 | `text.primary` | headline 17 及以上 | 页面标题、列表主文案 |
| 次 | `text.secondary` | body 17 / callout 16 / subheadline 15 | 副标题、说明、表单标签 |
| 三级 | `text.tertiary` | footnote 13 / caption1 12 | 时间戳、计数、非交互元信息 |

补两条约束：**三级色只用于非必需信息**；**占位符若承载「该填什么」的必要信息，用 `text.secondary`**——13 与 12 只差 1pt，颜色也接近，层级要靠「是否必需」分工，而不是再压一档颜色。

#### 8.4.4 文案注入要在 M1 定形态，不能只写「可注入」

`WDLocalization` 最小形态建议：key + 参数化 + 默认值；库里只出现 key 与默认值，不出现业务句子。`06 §3.2` 的 20 条句式降格为默认值（正好对应 §6.8 的契约 / 默认值分界）。这决定 37 个组件的 API 形态，比配色更难事后改。

### 8.5 两条平台侧空白（三方都没提）

**8.5.1 Android：Material You 动态取色会顶掉品牌蓝。** 宿主若把 `dynamicLightColorScheme()` 套在 `WDTheme` 外层，系统色会覆盖品牌蓝，跨端一致性直接失效，且每台设备颜色不同。建议 M1 明确「不接入动态取色」，`WDTheme` 内显式以 Wisdom 语义色覆盖，或提供 opt-in 开关并在文档写明后果。一条实现即可解决，但漏了就是线上事故。

**8.5.2 iOS 26：系统 chrome 与自绘 Tab 栏的关系要先验证。** 设计要「悬浮胶囊 Tab 栏」，而 iOS 26 的系统 Tab 栏自带收缩与形变行为；自绘会与系统 chrome 形成两套视觉语言，并失去系统级交互与无障碍支持。建议 M1 真机验证「复用系统 chrome + 令牌配色」能否达到设计意图；若可以，`02 §34` 的验收项（高 58 / 距左右 16 / 底部 8）应只约束自绘档（iOS 17–25 与 Android），iOS 26+ 改为「形态与系统一致 + 配色符合令牌」。这条影响 P0 组件，越早验证越好。

## 附录 B · 复算与审计命令

对比度复算（WCAG 2.1 相对亮度）：

```bash
node -e '
function lum(h){h=h.replace("#","");const f=c=>c<=0.03928?c/12.92:Math.pow((c+0.055)/1.055,2.4);
return 0.2126*f(parseInt(h.slice(0,2),16)/255)+0.7152*f(parseInt(h.slice(2,4),16)/255)+0.0722*f(parseInt(h.slice(4,6),16)/255);}
function cr(a,b){const l1=lum(a),l2=lum(b),hi=Math.max(l1,l2),lo=Math.min(l1,l2);return ((hi+0.05)/(lo+0.05)).toFixed(2);}
console.log(cr("#1677B3","#FFFFFF"))'
```
