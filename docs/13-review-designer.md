> 性质：第二轮三方独立复核中的**设计侧一份**。结论、数字与判定均自持：不复述第一轮结论当依据，重读了原文、重新读了令牌、重新渲染了设计稿、重新复算了对比度（见附录 A/B）。`12-review-architect.md` 与 `14-review-techlead-round2.md` **不作为本稿输入**；若个别结论重合，属独立同源发现。

### 1.2 方法（四步，每步都留痕）

1. **读原文**：文档之间交叉对读，重点抓"同一件事在两处写法不同"；
2. **读令牌**：把文档里出现的每个数值回到 `tokens/wisdom.tokens.json` 找它的家，找不到家的记为游离值；
3. **渲染**：用 headless Chrome 把预览页的**内层文档**提取出来（`data-srcdoc`），浅色与深色各渲一遍，再隔离出「渐变 · 材质 · 形状」那张 `.wd-canvas-sheet` 看色晕实际长什么样（命令见附录 B）；
4. **复算**：所有对比度按 WCAG 2.1 相对亮度公式重算，含 alpha 合成；色相/亮度按 HSL 与相对亮度算（脚本见附录 A）。

### 1.4 一条重要的范围限制：**"两端渲染"目前只能指浅/深两外观**

团队目标里写的"两端实际渲染"，在平台侧**现在拿不出东西**：

- iOS 仓库 5 个 Swift 文件，只有 `WDTokens.swift`（生成产物）、`WDColor+Hex.swift`、`WDTokenTypes.swift` + 1 个测试，**没有任何组件**；
- Android 仓库 4 个 Kotlin 文件：`WDTokens.kt`（生成产物）、`WDTheme.kt`、`WDGradient.kt` + 1 个测试，同样**没有任何组件**。

所以我这一轮的"实际渲染"复核 = **浅色端 / 深色端在预览页与画廊里的渲染**（这也是 `10-discussion.md` 与 `11-conclusions.md` 用"两端"时的含义：浅色端 / 深色端）。**平台侧的真实渲染验证仍是空白，且它是 M1 的出口**（`11-conclusions.md:153`）。这一条我写进 §6，作为"M0 开工前还差什么"的一部分。

### 1.5 两类问题，分开记账

本稿每条发现都标注性质，因为两类问题的处置方式和成本完全不同：

| 性质 | 定义 | 处置 | 本稿条目 |
| --- | --- | --- | --- |
| **设计方向问题** | 决定"做成什么样"的判断错了或缺失：语义色定义、层级分工、材质取值、多语言方向、字体；改它要重新裁定，改完要重出设计稿 | 设计侧给出替代方案 → 重新裁定 → 改令牌/规格 | D3 · D7 · D12 · D13 · D15 · D17 |

## 3. 设计方向结论

### 3.1 温和蓝：**成立，但"温和"现在的两个承重点都没落地**

成立的证据（浅色端实际渲染 + 复算）：

- 三段明度阶梯单调且拉开：`filled` 0.557 → 0.424、`canvas` 0.927（附录 A 第 5 组）；渲染图上按钮、卡片、页面底的关系读得出来；
- 语义色四种（成功 `#2A7F5C` / 信息 `#1677B3` / 警示 `#97651F` / 危险 `#B8564D`）在 `status-soft` 上的问题已由 B2 的 `status-text.*` 方案解决，方向正确（`10-discussion.md:365-373` 的复算我复现了：软底要拉到 0.957 才够，等于毁掉软底的语义，所以只能加深文字）。

**但"温和"现在挂在两个点上，而这两个点都还没兑现：**

1. **页面色晕的浓度**。用户前后三次说"再浅一点"，第一轮把 66% 降到 42%（`11:65`），设计稿仍是 66%（`preview:1381`）。更麻烦的是：**42% 这个数到底怎么落到像素上还不确定**（见 D1）。所以"温和"目前是**声明**，不是**观感**。
2. **三级色的层级方式**。三级色加深到 `#4C616D` 后，它与 `text.secondary #3E5764` 的对比度只差 1.18 倍（6.04 vs 7.10，我复算吻合），**"三级"必须改由字号承担**——而承载这条逻辑的映射表还不存在（§5.2），所以现在文档里三级色的用法仍是"随手降一档颜色"。

### 3.2 Liquid Glass：**方向成立，执行被三件事削弱**

`01-foundation.md:13-22` 的六特征在预览里有实现：`.wd-glassbase`（四件套：模糊 + 半透明 + 顶部高光描边 + 外圈 hairline，`preview:1403-1409`）与 `regular 70% / thick 86%` 的材质演示（`preview:1455-1459`、渲染图可见）。**"边缘高光 + 克制阴影"这两件做得对**，是"真玻璃"和"廉价毛玻璃"的分界（`01:18`），不要动。

削弱它的三件事：

1. **全屏色晕把"动态取色"变成了"固定蓝罩"**。玻璃透出的应该是下层内容的颜色（`01:21`），而设计稿里整个页面先被一层固定蓝罩盖住（`preview:1423`），玻璃透出的其实是蓝罩而不是内容；
2. **玻璃档位有三个数在打架**（D2 的账目表）：`01:284` 的 62/62/82%、`tokens:254-258` 的 38/54/70/86%、`preview:1363` 的 86%、画廊 `:1564` 的 88%；
3. **深色端玻璃透出的是浅色色晕**（D3）。这一条最严重：`08.2.1` 的 2.40 就是它造成的。

**结论：Liquid Glass 的"形态"不用改，要改的是"它浮在什么上面"——先把色晕的净 alpha 与深色派生源定下来，玻璃档位才谈得上验收。**

### 3.3 家庭工具调性：**成立，两个具体缺口**

"家庭"的承重件（成员头像、共享状态、任务归属、圆润图标底座、大圆角）都在：`02-components.md:77-90`、`specs/03-patterns.md` 的 R1–R5、`08-icons.md:39-44` 的图标底座。**"工具"的承重件（状态机、即时反馈、密度可控）也齐**（`09-layout.md:93-103` 的两档密度、`06:190-201` 的触觉与"同一次操作只给一次"）。

两个缺口：

1. **字体是"家庭感"最直接的载体，而现在它是矛盾的**：`01:175` 把 MiSans 称作"圆体候选"、`tokens:160` 把 `family.rounded` 写成 `SF Pro Rounded / MiSans`——**MiSans 不是圆体**（HarmonyOS Sans SC 也不是）。于是"Android 端的圆润家庭感"实际上落在一套非圆体上；而 A1（嵌入中文）之后这个问题更突出（见 §5.3）。
2. **RTL 完全空白**（3.5 节）。家庭工具的"多人共享"语境里必然包含阿拉伯语/希伯来语宿主；今天四份设计稿 **0 处 `dir=`、0 处 `rtl`**，等于这个方向没有设计。

### 3.4 深色端：**当前不成立**（这是本轮最硬的一条结论）

| 项 | 现况 | 复算 |
| --- | --- | --- |
| 深色色晕 | 与浅色**共用同一份浅色色卡**（`preview:1379` 注释"两套主题共用一份定义"，`:1380-1383` 三个色标无 `light-dark()`） | 叠在 `#0A1B2A` 上 → 最亮档合成 `#465F6C`；`text.tertiary #839EB0` **2.40** ❌、`text.secondary #A4BCCB` **3.42** ❌、primary 5.87 ✅ |
| "降浓救深色" | 不行 | 要让 tertiary 过 4.5，色晕 alpha 必须 **≤14%**（附录 A 第 3 组）；而 14% 的湖水蓝叠在深色底上合成 `#213543`，和底色 `#0A1B2A` 几乎看不出差别——**色晕等于不存在**。所以深色端只有"换派生源"一条路，`10-discussion.md:1017-1026` 的候选是对的 |
| A2 深色压向青灰 | 方向已定、色值待定（`11:31`） | 见 D15：`#0A1B2A` 色相 208.1°，su 阶 200–203°，浅色 `canvas` 193.3°；深色表面族无一取自 su 阶 |

**结论：深色端在 A2 的色值 + 深色色晕 + tertiary/secondary 三件事同时落地之前，不能宣称"深色版同批交付"（`01:35`）。** 我倾向于把"深色端达标"写成 M0 出口的**硬断言**，而不是"随 M1 验证"。

| 项 | 我第一轮的估计（`10-discussion.md:880`） | 本轮实测 |
| --- | --- | --- |

### 3.6 方向结论一句话

### D1 · 色晕"66% → 42%"的适用范围未定，且与 `opacity:.55` 的叠乘关系未定【账目 · 阻塞】

- **现象**：同一个决定在四处用了**两种不同的算法**，落成令牌时必然随手取值：
  - `11-conclusions.md:65` 只写"浅色色晕浓度 66% → **42%**"，没说另外两档怎么办；
  - `01-foundation.md:149` 写"透明度 **18–66%**"（是一个区间描述，不是三档配方）；
  - `10-discussion.md:745-750`（§6.5）的 42% 表是**直接把 42% 当生效浓度**（算出 `#D6E9EF`——我复算吻合，这是"42% 湖水蓝直接叠 canvas"的值，**没有乘 .55**）；
  - `10-discussion.md:995`（§8.1）却写"42% 合成色：湖水蓝 `#D6E9EF`、天青（**按比例 0.293**）`#CFE9ED`"——天青档用了 46% × (42/66) = 29.3% 的等比缩放，**这是第三种算法**。
- **同时**：预览里色晕的浓度不是由色标 alpha 单独决定的，还要乘一层元素透明度（`preview:1423` 的 `opacity:.55`），而第一轮的净 alpha 口径仍是开放项（`11:111`）。
- **量化后果**（附录 A 第 2 组）：第一档"42% 直接落"合成 `#D6E9EF`（相对亮度 0.789），"42% × .55"合成 `#E2F0F4`（**0.850**）——同一句话的两种读法，观感差一档。更要紧的是：**如果删掉 `.55` 而保留 42%，页面会比今天更浓**（今天生效 0.363，删掉后 0.42，合成 `#C1E2E8`，L=0.716），与用户"再浅一点"的诉求**反向**。
- **要求**：把"浓度"收敛成一个口径（见 §5.5 的结论），并在令牌里写**生效 alpha**；`11:111` 那条开放项随之关闭。

### D3 · 深色色晕共用浅色色卡，且"降浓"救不了深色端【方向 · 阻塞】

- **证据**：`preview:1379` 的注释就是自白——"场景底：半透明色晕叠在 light-dark 底色上，**两套主题共用一份定义**"；`:1380-1383` 三个色标是 `#B0D5DF 66% / #7EC4CF 46% / #4C8DAE 18%`，**没有一层 `light-dark()`**。令牌侧同因：`gradient.surface` 有浅深两套（`tokens:100`、`tokens:150`），但**色晕根本不是令牌**（`wash` 令牌不存在，`11:207`）。
- **后果复算**：深色底 `#0A1B2A` 上最亮合成档 `#465F6C` → tertiary **2.40**、secondary **3.42**（附录 A 第 3、4 组）。

- **要求**：`gradient.wash.dark` 由 `semantic.dark.gradient.surface`（`#123449 / #0F4055`）派生，取值 36%（`11:104` 候选，我复算吻合）；且 A2 的色值与之**同批判定**（D15）。

### D13 · `family.rounded = "SF Pro Rounded / MiSans"` 把非圆体当圆体【方向 · 中】

- `tokens:160`（`"rounded": { "$value": "SF Pro Rounded / MiSans" }`）与 `01-foundation.md:175`（"标题/数字（可选，增强家庭感）｜SF Pro Rounded｜圆体候选：MiSans / HarmonyOS Sans SC"）。

### D14 · `surface.card` 的自述与数值不一致（描述 96%，值是 94.1%）【账目 · 低】

- `tokens:62`：`"card": { "$value": "#FFFFFFF0", "$description": "96% 白，边缘干净…" }`。`0xF0 = 240`，`240/255 = **94.1%**`——**令牌自己的描述与自己的值差 2 个点**。

## 5. 设计侧必须补的规格（逐项结论）

### 5.1 tint 配方与基准底（对应 `11:193` 待验证确认第 6 项）

**结论（可直接抄进令牌）：**

```jsonc
// semantic.light.gradient.tint
{ "$value": "linear-gradient(135deg, #1677B3 16% over surface.card, #2A5CAA 12% over surface.card)",
  "$description": "次级操作底（tonal / Chip 已选 / Badge shared）。
                  基准底 = surface.card（名义白 #FFFFFF），不是 bg.canvas。
                  hex 由生成器算：浅色端 ≈ #D9E9F3 → #E3EEF6。" }
```

**三条理由，都是算出来的（附录 A 第 6 组）：**

1. **基准底必须是 `surface.card`**。tonal 按钮出现在卡片/列表容器里，它的下层是卡片。若基准底写 `canvas`，同一颗 tonal 在"卡片上"和"页面底上"会是两个颜色，生成器产出的值在页面上一定对不上（卡片本身是 94–96% 白叠在色晕上，`tokens:62`）。**基准底写 `card`；`canvas` 留给断言跑最不利值**——这正好满足 `11:139` 出口条件第 2 条"自动取最不利背景"。
2. **色族用品牌蓝，不用湖水蓝族**。设计稿 `#D5EBF6` 的色相是 **200°**、亮度 0.802；`#1677B3` 16% 叠白 → 色相 202.5°、亮度 0.795（ΔRGB 5.4，最接近）；湖水蓝 `#B0D5DF` 要 **48%** 才达到同样亮度，且色相只有 191°。更关键的是**语义**：湖水蓝/天青族正是页面色晕用的色（`preview:1381-1382`），拿它做按钮底会重演 §8.3.3 那个失败模式——**看起来像个比色晕更浓的背景块，而不是按钮**。
3. **配方要挂在"亮度阶梯"上，不能只挂在百分比上**。阶梯是 `filled` 0.56 / `tonal` 0.80 / `canvas` 0.93（`11:72`）。按"品牌蓝 20% 叠白"算出来是 0.752，**掉出 0.80 这一档**，与 `filled` 暗端 0.424 之间的空档从 0.24 缩到 0.19——阶梯就不单调清晰了。所以：**先把 0.80 定为约束，再反解 alpha**（品牌蓝 → ≈16%，湖水蓝 → ≈48%，天青 → ≈33%）。

**连带动作**：`tokens:258` 的 `material.tinted` 与 `01:281` 的"品牌色 24–30%"必须改成同一套配方口径，或明确 `material.tinted` 是"玻璃底上的品牌染色"（另一种语义，要单独命名，不能与 tonal 的 tint 混用同一句话）。

### 5.3 A1 中文字体：设计侧立场与四条设计后果

**产品裁定 A1 = 采用嵌入（`11:30`），覆盖了设计侧 S6 的"不嵌入"建议。设计侧执行这条裁定，但要把它翻译成一条可执行的形态。**

**设计侧最终立场（不是表态，是可验收的形态）：**

> **组件库零字体；"嵌入"落在产品层的品牌增强包。**
> 组件库只提供**字族令牌 + 降级链 + 字重回落表**；中文字体文件由产品 App 引入，库通过 `typography.family.cjk` 接收宿主注入的字族名。

理由（三条，都指向"谁承担代价"）：
1. 组件库被别的 App 引入时，**9MB+ 是所有宿主都要付的代价**，而"家庭感"是**一个产品的取舍**——这与 `specs/03-patterns.md:23-24`"库和产品耦合会让别的 App 觉得是废物"是同一条判断；
2. iOS 与 Android 的字体授权、子集化能力、系统级降级规则都不同（`11:185` 列的 MiSans / HarmonyOS Sans SC 商用授权就是其一），**把它做成组件库的硬依赖，会让"跨端一致"这个设计目标变成发布风险**；
3. 架构师 `10-discussion.md:1145` 给的"组件库零字体 + 产品层可选增强"是可执行形态，**设计侧同意**；差异只在于：我把"产品层嵌入"设为**默认推荐**，而不是"可选"——因为 A1 已经裁定要嵌入。

**A1 的四条设计后果（必须写进 M0 的字体规格，否则嵌入了也没有设计效果）：**

| # | 后果 | 设计要求 |
| --- | --- | --- |
| 1 | **字族令牌要能表达"中文和西文是两套"** | 现 `tokens:158-161` 只有 `sans` / `rounded` 两个字族；需补 `family.cjk`（含降级链），并把 `rounded` 从"圆体/中文"的混写里拆出来（见 D13） |
| 2 | **字重缺档必须定义回落** | 现令牌用到 400 / 500 / 600 / 700（`tokens:162-173`）；中文子集化常缺 500（`overline` / `caption2` 用 500）。必须写"缺 500 → 回落 400 还是 600"，否则 Android 端 `overline` 会静默变细 |
| 3 | **行高比必须按中文字面率重取** | 中文的推荐行高比高于西文；现 `type.subheadline` 是 20/15 ≈ 1.33、`footnote` 18/13 ≈ 1.38，而 `body` 只有 1.29（`tokens:167,169,170`）。中文正文 1.29 偏紧，且**两行截断的说明文字**（`01:198`）最容易读到挤。建议：M0 冻结 `lineHeightRatio` 时，**分别给出 CJK 与拉丁的比例**，并在 M1 的六态截图里验证 AX3 下不截断 |
| 4 | **数值必须继续走西文字族** | `01:199` 要求金额/计数用等宽数字（`tnum`）；中文无衬线字体对 `tnum` 的支持不一致。**裁定：数值一律用 `family.sans`（SF Pro / Roboto Flex），CJK 字族只承担汉字**。这条要写进 `01 §4.1`，否则"嵌入中文"会顺手把数值的等宽特性弄丢 |

**一句给产品的话**：A1 已经定了"要不要嵌入"，但**"嵌入之后设计上要重新取的三个值"（字重回落、行高比、数值字族）必须进 M0 的同一批冻结**，否则 M1 的 `WDTextStyle` 冻结会在一套没有中文约束的数值上完成，M2 之后 37 个组件全部返工。

### 5.5（附加）页面色晕的最终写法与净 alpha —— 这条必须先定，因为它是 D1/D3 的收口

**结论：令牌写"生效 alpha"，预览删掉元素透明度，浅色三档按等比缩放。**

```
gradient.wash.light  = 23% 湖水蓝 / 16% 天青 / 6% 群青   （生效 alpha，可等比还原 42/29/11.5 的名义值 × .55）
gradient.wash.dark   = 36% #123449-derived（由 semantic.dark.gradient.surface 派生）
```

**取 23% 而不是 42% 的理由（这是 D1 的正面回答）**：今天的实际观感是 `66% × .55 = 36.3%`；`42% × .55 = 23.1%` 是"更浅"（合成 `#E2F0F4`，L=0.850 > 0.807）；而"删掉 `.55` 只留 42%"会变成 **42%**，比今天**更浓**（合成 `#C1E2E8`，L=0.716），与用户三次"再浅一点"反向。**所以"66% → 42%"这句话只有在"仍乘 .55"的读法下才成立**——首轮把这个隐含前提留在了开放项里（`11:111`），本轮把它关掉：**令牌直接写 23%，预览删除 `preview:1423` 的 `.55` 与 `preview:1468` 的 `.5`。**

**为什么删元素透明度而不是保留**：同一个 `--wd-wash` 在预览里已经被两处不同的元素透明度用了（`.55` 与 `.5`），说明"浓度"确实没有单一真源（D2 同类）。而且元素透明度会让"色标 alpha"和"元素 alpha"两个数在任何断言、生成器、两端实现里都要乘一遍——这正是 `10-discussion.md:1029-1037` 要求"取最不利必须落成算法"想避免的人工复算点。

**顺带确认一条让 M0 变简单的结论**：净 alpha 口径**不再影响达标结论**——我用 `#4C616D` 把五种口径（A 等比缩放 / B 只改第一档 / C 生效 alpha / D 直删 `.55` / 现况）都跑了一遍，三级色最不利值分别是 5.52 / 5.23 / 5.53 / 4.61 / 5.23，**全部 ≥4.5**（附录 A 第 2 组）。所以这条可以在 M0 直接按"设计观感"定，不必等断言——**但它必须定，否则四个可视化产物各写一套**。

## 7. 未决问题

1. **Tab 栏未选标签的层级**（§5.2 例外清单第 1 条）。我裁定改为 `text.secondary`，与第一轮"只修 tertiary 深色侧数值"的处理不同。**需要队长/三方确认**——如果保留 `text.tertiary`，则三级色映射表必须为它开一条"11pt 例外"，规则的可验收性会下降。
2. **A2 的目标色值与范围**（D15）。"压向青灰"必须落成可断言的口径（建议：深色表面族统一取 su 阶色相带 200–203°），且**范围是整套深色表面族**，不是单个 `bg.canvas`。色值本身仍需**用户**拍板。
3. **A1 的落地主体**：设计侧主张"组件库零字体 + 产品层增强包"（§5.3），与产品裁定的"采用嵌入"在**实现主体**上需要产品确认——裁定的是"要不要"，我补的是"谁付体积"。
4. **`material.tinted` 与 `gradient.tint` 是不是同一件事**（§5.1 连带）。我的理解是两种语义（玻璃上的品牌染色 vs 实底上的次级操作底），如果是，二者必须**分开命名**，不能继续共用"品牌色 N% 叠加"这一句描述。
5. **RTL 的镜像判断终审**（D11）：44 行对照表逐行判断需要一次设计评审（`chevron.*` / `arrow.uturn.*` / `list.bullet` 镜像；`clock` / `calendar` / `heart` / 播放暂停类不镜像），我给出的是判断规则，**具体到每一行的结论要留痕**。
6. **预览页的定位**（D7）：是"设计真源的可视化产物"（那么必须由令牌生成），还是"仅浅色端的示意页"（那么删掉深色切换与游离去重值）？这个定位决定 M0 出口 ① 的范围，**建议在 M0 开工前明确**。
7. **色卡是否需要"被消费关系"列**（§5.4 末尾）：加了它，"群青降级"（B1）这类裁定才有落点；不加，色卡永远只是对照表。**我建议加**，但它是文档结构变更，需要三方同意。

## 附录 B · 渲染复核方法（可复现）

预览页是"外层包装 + iframe `data-srcdoc`"结构，所以先把内层文档解出来再渲染：

```bash
# 1) 解出内层文档
node - <<'JS'
const fs = require('fs');
const s = fs.readFileSync('design/preview/wisdom-light.html', 'utf8');
const m = s.match(/data-srcdoc="([\s\S]*)">\s*<\/iframe>/);
const u = x => x.replace(/&lt;/g, '<').replace(/&gt;/g, '>')
                .replace(/&quot;/g, '"').replace(/&#x27;/g, String.fromCharCode(39))
                .replace(/&amp;/g, '&');
fs.writeFileSync('/tmp/preview-inner.html', u(m[1]));
JS
# 2) 渲染（浅色；深色把 appearance: "light" 改成 "dark"、class="wd-light" 改成 "wd-dark"）
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu \
  --user-data-dir=/tmp/dsh-chrome-profile --window-size=1000,900 --timeout=8000 \
  --screenshot=/tmp/only-light.png "file:///tmp/preview-inner.html"
```

观察结论（E2，仅作"看上去是什么样"的佐证，数值结论一律以附录 A 的复算为准）：

- 浅色端：`.wd-canvas-sheet` 左上有一层淡蓝罩，**浓到能看出色相**（对应 36.3% 的生效浓度）；
- 「材质 Materials」一行能看到四档从透到实（对应 38/54/70/86%），其中 `tinted` 是浅蓝渐变块（对应 `preview:1459` 用的 `gradient.surface` + 50% 白，**不是** tint 配方）；
- 深色端：色晕罩仍来自浅色色卡，页面被抬亮（对应 D3 的合成 `#465F6C`）；
- 画廊三份 HTML 里 **没有页面色晕**（唯一的 `radial-gradient` 是点阵背景，`gallery/wisdom-components.html:612`），也就是说**在画廊里评审组件，等于在唯一理想的平铺背景上评审**——最不利背景不会暴露。这条已并入 D16（可视化产物的可信度）。
