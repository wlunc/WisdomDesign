## 0. 计划原则

### 0.1 按出口条件推进，不用文档数量或人日代替完成

- 每个阶段先满足入口条件，再开始实施；
- 每个任务必须给可执行验收；
- 每个阶段有明确交付物和未验证项；
- 不预设人力和工期承诺，优先级与依赖关系由里程碑表达；
- 设计、iOS、Android 可并行准备，跨端契约与版本裁决是串行点；
- 只有原生证据齐全，平台状态才能升级。

### 0.2 首版采用纵向切片

不先做“37 个组件 + 四个模板 + 全平台”的大而全版本，而是：

```text
一个 Page Spec
→ 一个 Core 组件目录
→ 每端少量真实 API 卡
→ 每端一个黄金页面
→ 两种 Skill 平台包
→ 固定生成任务对照实验
```

证明闭环后，再扩组件、页面模式和平台。

### 0.3 角色

| 角色 | 责任 |
| --- | --- |
| 设计负责人 | 页面语义、组件用途、黄金页面、设计评审与视觉验收 |
| 架构负责人 | Page Spec、Provider SPI、版本与构建契约、跨仓依赖 |
| 工具开发 | CLI、提取、渲染、查询、脚手架、打包和测试 |
| iOS 负责人 | iOS Provider、真实 API、模板和原生验证 |
| Android 负责人 | Android Provider、真实 API、模板和原生验证 |
| 消费方 App 负责人 | 工程接入、业务模板落点、消费侧构建与维护性 |
| QA / 验证负责人 | 测试矩阵、报告、反例和回归 |
| AI 评测负责人 | 固定任务、模型与成本记录、Baseline 对照实验 |
| 发布负责人 | 产物签名 / 校验、版本、发布说明与安装验证 |

小团队可一人兼多角，但**同一实现不得由本人单独完成最终评审**。

## 3. M0：契约冻结与实施准备

### 入口

- 用户批准进入实施；
- D1–D10 待拍板项有明确结论或默认执行项；
- 三仓基线 commit 与已有 dirty 修改被记录；
- 不覆盖任何现有用户修改。

### 任务

#### M0-1 冻结 Page Spec v1

**范围**：只含页面意图、导航、内容模式、区域、状态、无障碍意图、验收和平台 overrides。

**验收**：

- JSON Schema 可验证；
- 至少一个正例和一个完整状态页面通过；
- 未知组件、无主操作、多主操作、集合缺空态等反例按约定处理；
- 不包含 Swift / Kotlin 类型；
- 明确单平台任务可跳过 Page Spec；
- schema 版本与 Skill / Token / 组件库版本分离。

#### M0-2 冻结 Provider SPI v1

**验收**：

- iOS、Android 各自 capability 字段可以表达；
- API 证据等级为 contract-only / discovered / example-compiled / template-verified；
- Provider 无法靠自填 `verified` 绕过证据；
- 不支持能力有明确返回结构；
- 路径与命令不隐式跨仓写入。

#### M0-3 建立真源映射表

**验收**：

- 37 份 YAML 与 37 个正式组件规格一一对应；
- R1–R5 只作为配方，不混入组件数；
- 组件用途、反例有稳定提取锚点；
- 旧 `02-components.md` 仅作历史资料，不进入组件生成目录；
- 每个字段有唯一来源和冲突裁决；
- iOS / Android 实际实现覆盖独立统计，不预设为 37。

#### M0-4 冻结包结构与 manifest

**验收**：

- Core / iOS / Android / All 包边界明确；
- manifest 有来源 commit、dirty、hash、版本、状态和 coverage；
- 不包含时间戳、绝对路径等破坏可复现性的字段；
- 所有状态与证据关系有测试用例设计；
- 首版宿主加载格式已确认，或明确先做通用包。

#### M0-5 选择双端黄金页面和验收矩阵

**默认候选**：设置表单或任务列表，由设计与双端负责人共同裁定。

**验收**：

- 同一份 Page Spec 可表达两端；
- 明确 loading / content / empty / error；
- 明确浅深色、大字体、长短内容；
- 明确平台返回、Safe Area / Insets、键盘 / 滚动和读屏；
- 每端验证命令来自当前构建系统，不使用不存在的任务；
- 人工设计评审表与自动测试表分开。

#### M0-6 冻结评测协议

**验收**：

- 固定任务输入、模型、推理参数、宿主、工具和超时；
- 有现有方式、精简规则、Skill 三种实验臂；
- 指标包含质量、修复、Token、工具调用和耗时；
- 明确缓存和成本口径；
- 不在没有样本时承诺固定节省比例；
- 原始日志和最终 diff 可保存。

#### M0-7 实施工作区与变更边界确认

**验收**：

- 每个任务标出可写仓和路径；
- 平台生成物只能由既有所有者工具更新；
- 不自动修改 iOS / Android 组件 API 或 ABI；
- 流水线默认只读平台仓；
- CI 不自动提交生成结果或基线。

### M0 出口

D1–D10 有记录；上述契约和测试计划评审通过；没有悬空真源、版本、模板归属或验证责任。

## 4. M1：Core Skill MVP

### 入口

M0 出口通过；提取锚点、包格式和 CLI 契约冻结。

### 任务

#### M1-1 建立只读设计提取器

**范围**：Token 摘要、YAML、正式 specs、布局 / 无障碍 / 内容结论、overlay。

**验收**：

- 使用 Ruby 标准库或获批依赖读取 YAML，不手写 YAML 解析器；
- 37 组件集合与 YAML 完全相等；
- 组件 ID、用途、反例、状态和来源可追溯；
- 缺章节、重复 ID、未知引用均失败；
- 不读取 HTML 画廊作为规范；
- 对非法输入返回非零退出码。

#### M1-2 生成组件目录和独立语义卡

**验收**：

- 目录支持短行全量扫描；
- 每张语义卡按组件单独读取；
- 用途 / 反例优先来自 specs；
- overlay 不覆盖视觉数值与 API；
- 无用途、来源断链或组件重复时构建失败；
- 输出不包含平台 API 猜测。

#### M1-3 实现 Page Spec 校验器

**验收**：

- 正例通过；
- JSON 语法、schema、未知字段、未知组件、非法导航 / 内容模式有反例；
- 错误含 code、JSON path、message、suggestion；
- 集合页空态规则有正反例；
- 退出码稳定；
- 明确报告“结构通过，不代表原生编译或视觉通过”。

#### M1-4 实现 Core 查询运行时

**验收**：

- 按 canonical 名称精确查询；
- 关键词查询返回有上限的候选；
- 不存在组件返回可操作建议，不编造相近 API；
- 默认不整份输出所有语义卡；
- 输入路径不能逃逸 Skill 包；
- 输出可被人和机器读取。

#### M1-5 渲染薄 Core Skill

**验收**：

- 三种模式路由存在；
- Core 模式不加载平台 API；
- 真源禁读清单与来源优先级明确；
- 不确定、不兼容和未验证时停止；
- 常驻入口预算有自动检查，预算值由实测与宿主约束确定；
- 所有按需引用无死链。

#### M1-6 Core 确定性构建与反漂移

**验收**：

- `build`、`check`、`test` 可执行；
- `check` 在临时目录重建并比较，不覆盖正式产物；
- 同输入连续两次构建一致；
- 生成文件带 banner 与来源；
- 无绝对路径、机器信息、缓存和临时文件；
- 非法输出路径被拒绝。

### M1 交付

- Core 生成器与测试；
- Page Spec schema 与校验工具；
- 组件目录和 37 张语义卡；
- Core Skill 目录包；
- Core 构建报告。

### M1 出口

Core 从干净输入可复现构建；全部正反例通过；37 个设计组件映射齐全；不代表任何平台 API 已验证。

## 5. M2：iOS 原生纵向切片

### 入口

M1 通过；iOS 基线和已有 dirty 修改隔离；黄金页面及消费方工程落点已确认。

### 任务

#### M2-1 建立 iOS Provider

**验收**：

- 从当前 Package / 源码 / 构建配置提取平台事实；
- iOS 17 基线与 iOS 26 能力 / 降级明确；
- Safe Area、Dynamic Type、键盘、滚动、返回和效果配额有落点；
- Provider 不复制设计数值真源；
- 未实测能力标未验证。

#### M2-2 生成 iOS API 卡

**验收**：

- 从公开 symbol graph / API 快照按组件分组；
- 覆盖 View 扩展和组件关联类型；
- canonical 参数与真实 iOS 标签分开；
- 重载不被 YAML 参数并集取代；
- 黄金页面涉及的组件和 modifier 都有卡；
- 快照与当前工作树不一致时显式报警，不能静默当成当前版本。

#### M2-3 建立最小调用例并编译

**验收**：

- 黄金页面涉及组件有最小消费例；
- 在消费方 target 编译，不只检查文本；
- 使用正确的 iOS 模拟器 / xcodebuild 流程；
- 不通过 host `swift build/test` 冒充 iOS 门禁；
- 编译命令、SDK、目标和结果入报告。

#### M2-4 建立 iOS 黄金页面模板

**验收**：

- 使用真实公开 API，不访问组件库 internal；
- 页面包含规定状态；
- 有明确业务修改区和受控模板标识符；
- 不默认改业务 App 导航、签名和依赖；
- 不包含组件库 Demo 私有辅助类型；
- 使用语义色和正确文字入口。

#### M2-5 实现脚手架安全复制

**验收**：

- 仅复制到明确目标；
- 默认拒绝覆盖；
- 非法页面名、路径逃逸、目标不存在有反例；
- 不执行模板内脚本；
- 复制后可通过消费方命令编译；
- 不自动删除或清理其它文件。

#### M2-6 执行 iOS 运行时矩阵

**验收**：

- 按黄金页面约定执行快照 / UI 测试；
- 至少区分已跑、失败、未跑；
- 遮挡、键盘、焦点、滚动和读屏按页面类型验收；
- 浅深色和大字体有结果；
- 真机未测项明确列出；
- 设计负责人完成独立视觉评审。

#### M2-7 生成 iOS Skill 包

**验收**：

- 只包含 Core + iOS；
- 不加载 Android 数据；
- manifest 标实际证据状态；
- iOS 查询、API 卡和脚手架在生成包内可运行；
- 缺平台工程时明确失败，不伪报验证通过。

### M2 交付

iOS Provider、真实 API 卡、最小编译例、黄金页面、iOS Skill 目录包、原生验证报告。

### M2 出口

从 Skill 包复制出的黄金页面在消费侧编译并满足已声明矩阵；结构、编译、运行时和设计结论分别报告。

## 6. M3：Android 原生纵向切片

### 入口

M1 通过；Page Spec 不依赖 iOS；Android 基线与可用构建命令确认。M2 与 M3 可在 M0 后并行准备，但跨端模型需在 M3 联验。

### 任务

#### M3-1 建立 Android Provider

**验收**：

- compileSdk / minSdk / Compose 等来自实际构建配置；
- WindowInsets、IME、系统 / 预测式返回、fontScale、TalkBack 有平台表达；
- Android 12+ 与其它版本的效果能力和降级按真实实现记录；
- 触控布局盒与 iOS 可见行高差异不被错误“对齐”；
- 未实测项明确列出。

#### M3-2 生成 Android API 卡

**验收**：

- 从真实 Kotlin 公开声明与 ABI 基线交叉提取；
- 保留 Composable、Modifier、状态提升和默认参数；
- 不从 Swift API 或 canonical YAML 猜 Kotlin 签名；
- 二进制 ABI 不能证明的源码形态标限制；
- 黄金页面涉及组件有真实来源；
- 缺失组件标 unsupported / spec-only，不生成假实现。

#### M3-3 建立最小调用例并编译

**验收**：

- 黄金页面涉及组件有真实包名和 import；
- 使用消费方或获批 fixture 编译；
- 与 ABI `.api` 基线兼容；
- 不运行不存在或已被新构建系统淘汰的任务；
- 命令、环境、结果和未验证项入报告。

#### M3-4 建立 Android 黄金页面模板

**验收**：

- 同一 Page Spec 映射为 Compose，而非翻译 SwiftUI；
- 使用平台状态、Insets、返回和字体行为；
- 不访问 internal API；
- 不引入未批准依赖；
- 不把 Material 3 默认样式当作 Wisdom 组件替代；
- 规定状态和平台交互完整。

#### M3-5 执行 Android 验证矩阵

**验收**：

- 编译 / 单测 / ABI 等已有门禁通过；
- 按可用基础设施执行截图 / UI；
- 浅深色、字体缩放、长短内容、键盘、返回和读屏分别报告；
- 真机未验证项不省略；
- 设计负责人独立评审视觉重量与跨端语义一致性。

#### M3-6 生成 Android Skill 包

**验收**：

- 只包含 Core + Android；
- 不加载 SwiftUI API；
- 查询和脚手架可在包内运行；
- 平台覆盖与证据状态真实；
- 同一 Page Spec 的双端差异在报告中可追踪。

### M3 交付

Android Provider、API 卡、编译例、Compose 黄金页面、Android Skill 目录包、原生验证报告。

### M3 出口

同一 Page Spec 在双端可分别实现；Android 黄金页面有真实编译与规定验证；共享语义与平台自由项无混淆。

## 7. M4：跨端组装、确定性打包与宿主验收

### 入口

M2 与 M3 至少有明确的验证证据；包结构和版本策略无未决冲突。

### 任务

#### M4-1 生成四种产物

**验收**：

- Core / iOS / Android / All 目录均可独立使用；
- All 复用已有生成内容；
- 不包含其它平台冗余常驻上下文；
- manifest 正确标各平台 coverage / 状态；
- spec-only 平台不会被路由到代码生成。

#### M4-2 实现确定性 ZIP 与 checksums

**验收**：

- 文件排序、权限、时间戳与换行固定；
- 相同输入重复打包哈希一致；
- ZIP 路径安全，无绝对路径和 `..`；
- 逐文件与整包 hash 可校验；
- 排除缓存、秘密、本地配置与临时文件。

#### M4-3 干净环境安装 / 加载验证

**验收**：

- 目标 AI 宿主能发现或按正式方式安装；
- 触发范围正确，不劫持无关任务；
- Core、iOS、Android 路由正确；
- 引用路径与运行时脚本在安装后可解析；
- 包升级和版本不匹配有明确提示；
- 没有目标宿主自动安装规范时，只声明通用目录包已验证。

#### M4-4 版本兼容与负向测试

**验收**：

- Token / Contract / Provider / 模板不兼容时失败；
- dirty snapshot 不能标 release；
- 缺失 API 卡、模板、脚本有明确错误；
- 不受支持平台只出设计结果；
- 错误报告不会建议编造组件或绕过测试。

#### M4-5 CI 接入

**验收**：

- PR、变更范围、深度原生与发布门禁分层；
- `check` 不改真源、不自动提交；
- 原生测试由对应平台仓负责；
- 文档改动不伪报原生测试；
- 构建报告可作为 CI artifact 保存；
- 发布需显式批准。

### M4 出口

四类产物可复现、可校验、可按声明方式加载；跨端与版本负向行为符合方案。

## 8. M5：真实 AI 对照评测与设计验收

### 入口

目标宿主可加载；固定任务集与实验协议冻结；构建和测试工具可自动执行。

### 任务

#### M5-1 建立固定任务集

至少包含：

1. 任务列表页；
2. 设置表单页；
3. 带空态 / 错误态的详情页；
4. 同一 Page Spec 的 iOS + Android 双端任务；
5. 过期组件名与不存在的 API；
6. 不支持平台 / 能力；
7. 已有页面的局部修改；
8. 长文案、大字体和键盘边界场景。

#### M5-2 运行三种实验臂

- A：现有项目资料，按现有方式生成；
- B：精简规则文档，无确定性工具；
- C：生成的 Skill。

**控制变量**：同模型、同推理参数、同需求、同宿主、同工程基线和同测试。

#### M5-3 自动质量评估

**验收**：

- 编译和测试原样记录；
- 统计 API 幻觉、失败类型和修复轮次；
- 状态矩阵与平台测试结果可复算；
- 最终 diff 和人工修改量保留；
- 工具调用、Token、缓存和耗时完整；
- 失败样本不删除。

#### M5-4 独立设计评审

**维度**：

- 用户任务与信息架构；
- 主操作与视觉层级；
- 组件选择与组合；
- 密度、间距、内容层级；
- 状态完整性；
- 平台原生性；
- 无障碍和内容质量；
- 双端语义一致而非像素强求一致。

评审者不只检查 lint；问题按 blocker / high / medium / low 记录。

#### M5-5 根据证据修正流水线

- 优先修复错误真源、路由、API 卡和模板；
- 不用增加更多提示词掩盖工具缺陷；
- 不通过放宽测试或删除困难样本提高指标；
- 重新构建并执行受影响回归；
- 记录每次规则和阈值调整原因。

### M5 出口

报告能回答：

- 是否减少不存在的组件 / API；
- 是否提高首次编译与状态测试通过率；
- 是否减少人工修改和设计问题；
- 是否降低端到端 Token 与修复轮次；
- 哪些任务仍然不适合自动生成；
- 收益在哪些样本和条件下成立。

样本不足时只出观察报告，不作普遍承诺。

## 9. M6：覆盖扩展与持续治理

### 9.1 组件覆盖

按黄金页面和真实需求优先级扩展，而非只追求数量：

```text
设计语义覆盖
→ 平台公开 API 发现
→ 最小调用例编译
→ 模板使用验证
→ 快照 / UI 覆盖
```

每一层单独统计。平台缺失组件仍保持显式状态。

### 9.2 页面模式扩展

优先级建议：

1. 列表与筛选；
2. 表单与编辑；
3. 详情；
4. 概览；
5. 模态任务；
6. 空态 / 新手引导与失败恢复。

每新增模板必须完成消费侧编译、状态矩阵、设计评审和负向脚手架测试。

### 9.3 新平台接入

新增平台只新增 Provider、能力画像、API 适配器、模板、Token / 组件映射和验证。没有真实实现与验证工具时只能 spec-only。

### 9.4 发布治理

- Skill、Page Spec、Provider、模板独立版本；
- 变更说明包含输入和兼容范围；
- 所有 verified 状态有证据；
- 发布包可从干净输入复现；
- 质量和 Token 趋势按固定任务追踪；
- 旧版本升级和失效提示明确。

## 15. 最终完成定义

本开发计划的最终目标不是“仓库里出现一个 Skill 文件夹”，而是：

> **设计和平台真源变化后，可以自动、可复现地生成兼容的 Skill；AI 在实际宿主中按需使用它，分别生成原生页面；结构和原生测试可执行；能力缺口会显式降级；质量和 Token 有真实对照数据；所有发布声明可审计。**

在此之前，所有阶段只声明各自已证明的范围，不把方案、静态生成或单端样板扩大描述为整个跨端系统已完成。
