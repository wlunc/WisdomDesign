## 0. 一句话结论

**这套规范作为「设计质量基线 / 组件库开发契约 / 人工评审依据」严谨且可执行；但作为「AI 直接生成新 feature 页面」的默认输入，缺少页面装配层、平台适配层和可执行验收闭环。**

推荐方向不是继续增加面向 AI 的规范副本，而是：

> **设计语义跨端统一，页面表达平台中立，代码生成与验收平台原生。当前多仓项目是 Skill 的编译输入和验证环境，Skill 是自动生成的发布产物。**

核心原则：

- 保留 Page Spec 作为跨端设计交换与验收意图，不把它做成跨端 UI 虚拟机；
- 共享组件语义，不统一 Swift / Kotlin 等平台的调用签名；
- 组件选择目录、组件语义卡与平台 API 卡分离；
- 原生模板由确定性工具复制，AI 只实现业务差异；
- 结构合规、真实编译、运行时表现和人工设计评审分别验收；
- 没有真实平台实现与验证能力时，只支持设计描述，不宣称支持代码生成；
- 所有 AI 消费产物由真源生成、带版本与来源、可复现并接受反漂移检查。

## 1. 现状评估：这套规范强在哪

- **三层令牌 + 唯一真源**：原始 / 派生 / 语义三层，DTCG 格式，生成器与 `build.js --check`，「界面只用 `semantic.*`、组件实现不允许写字面量」能落地。见 [项目说明](../README.md) 与 [设计令牌](../tokens/wisdom.tokens.json)。
- **规格能当开发契约**：37 个组件采用统一规格模板，覆盖用途、反例、尺寸、状态、内容、交互、无障碍和验收。见 [组件规格索引](../docs/specs/README.md)。
- **契约机器可读**：37 份 [组件契约](../contracts/README.md) 登记参数并集、槽位、语义默认和枚举，配有校验工具。
- **布局规范指出了真正的问题**：组件解决「这一块长什么样」，布局解决「这些块怎么排」；组件都对，页面仍可能很挤或很散。见 [布局与响应式](../docs/09-layout.md)。
- **配方边界成熟**：R1–R5 不进组件库，避免业务语义污染发布 API；验收强调边界数据，而非只验正常态。见 [场景配方](../docs/specs/03-patterns.md)。

问题在于：现有真源主要提供「零件和原则」，AI 生成页面还缺「整机装配图、平台工程约束和生成后验证」。

## 2. 直接用于 AI 页面生成的六个问题

### 2.1 缺页面级装配产物

当前有：

- 令牌、组件契约和详细规格；
- 三种导航骨架、间距与密度规则；
- R1–R5 家庭工具业务配方；
- 组件陈列画廊与平台组件 Demo。

当前缺：

- 平台中立的页面结构表达；
- 已编译验证的原生页面模板；
- 跨端页面模式与组件组合索引；
- 覆盖 loading / content / empty / error 的完整页面正例；
- 从设计意图到消费方工程的明确边界。

iOS [DemoCompositionView.swift](../../iOS/Examples/WisdomUIDemo/WisdomUIDemo/DemoCompositionView.swift) 已有真实组件组合，但它是组件库 Demo，不应直接成为业务页面模板真源。

### 2.2 全量输入的 Token 成本高且信噪比低

初版估算曾按中文 1–1.6 token/字、ASCII 0.25–0.3 token/字节，对文档、YAML、Token 与 HTML 画廊做了 26–35 万 token 的全量读取粗估。这个数字只用于说明「全量塞入不可取」，**不是实际单次生成任务的真实基线**。

主要高噪声来源：

- 评审历史、阻塞项、排期与产品裁定；
- 设计取值的论证和审计过程；
- 跨端副本审计、变更流程和提交历史；
- HTML 画廊源码与 PWA 副本；
- 与当前目标平台无关的 API。

AI 通常需要设计结论、真实 API、一个页面正例和验证反馈，而不是这些资料的原文。

### 2.3 多套口径会污染源生成结果

已核对的典型问题：

- [旧组件清单](../docs/02-components.md) 仍标 v0.1，包含未注册组件和过期名称；
- A/B/C 编号、WD 名称和 01–37 规格编号并存；
- [契约说明](../contracts/README.md) 记录了 default 键、重载、槽位出处等已知偏差；
- 枚举统计在文档章节间存在不同口径；
- YAML 的 `params` 是重载并集，不能直接还原某一个真实构造或函数。

因此不能让模型自行在旧清单、契约、规格和平台源码之间猜测优先级。

### 2.4 组件库契约不是页面调用说明

AI 选组件需要：

- 用途、反例和替代组件；
- 变体、状态和内容语义；
- 适合哪个页面区域；
- 如何组合。

AI 写代码还需要：

- 当前平台的真实公开符号；
- 重载、参数标签、类型、必填性与默认值；
- View / Modifier / Composable 等调用形态；
- Binding / 状态提升；
- 关联类型和最小可编译调用例。

这两类知识必须分层提供。

### 2.5 缺统一 AI 入口和生成后的自证闭环

现有平台 `AGENTS.md` 是组件库施工手册，不是业务页面生成入口。已有 Token / contract 校验主要验证仓库内部一致性，不能证明新页面：

- 组件与 API 使用正确；
- 原生代码可以编译；
- 键盘、遮挡、焦点、滚动和读屏正确；
- 浅深色、大字体和平台降级合格；
- 信息架构与业务状态合理。

### 2.6 技术栈和平台能力可能错配

iOS、Android、Web / H5 的导航、状态、返回、Insets、字体缩放、无障碍和效果能力不同。后续平台不能直接照搬 SwiftUI / Compose 契约，也不能由 iOS 代码机械翻译得到。

## 3. 初版提案的评审与修订结论

初版提出的独立 AI 消费层、按需检索和可执行校验方向应保留，但以下设计需要修订。

| 初版建议 | 结论 | 当前方案 |
| --- | --- | --- |
| 新增独立 AI 消费层 | 保留 | 只保存派生物和必要 overlay，不复制设计真源 |
| 入口路由、按需检索、生成物 `--check` | 保留 | 扩展为 Core + Provider、版本化和可复现构建 |
| 生成后必须执行校验 | 保留 | 拆成语义结构、平台编译、运行时与设计评审 |
| 紧凑索引删除平台类型、参数名和重载 | 修订 | 选择目录可删；平台 API 卡必须保留真实调用信息 |
| YAML 作为平台签名真源 | 修订 | YAML 管跨端语义；平台公开符号 / 源码 / ABI 管真实调用 |
| `page.json → 平台代码` 为唯一主路径 | 修订 | Page Spec 用于交换和验收；原生模板与 Provider 负责实现 |
| 先做全部入口、索引与规则，模板和校验随后 | 修订 | 先做 M0 契约，再用一个双端黄金页面验证纵向闭环 |
| 固定节省 90–95%、常驻 2k–6k | 不作为承诺 | 用固定任务实测端到端 Token、工具调用与修复轮次 |
| 37 条用途 / 反例全部新增手写 | 修订 | 优先从正式 specs 提取，人工补检索和组合语义 |
| 四个页面骨架混合导航与表单 | 修订 | 导航骨架与内容模式分开建模 |
| 静态页面 lint 证明合规 | 修订 | lint 只证明可静态判断的部分，不冒充编译或视觉验收 |

### 3.1 为什么平台 API 卡不能删除真实类型

以 [WDButton 契约](../contracts/WDButton.yaml) 为例，canonical `loading` 对应 iOS `isLoading`，且真实实现存在多个便利构造。弹层差异更大：[WDBottomSheet.swift](../../iOS/Sources/WisdomUI/Components/Composites/WDBottomSheet/WDBottomSheet.swift) 的消费入口是挂在锚点视图上的 `.wdSheet(...)`，不是普通 `WDBottomSheet(...)` View。

只有组件名、槽位和枚举，AI 可以「选对组件」，却不能稳定「写对调用」。

### 3.2 为什么静态检查不能等同于页面正确

以下事项需要原生渲染或交互证据：

- 封装组件内部是否引入第二个纵向滚动容器；
- Tab / 底部操作条是否遮挡内容，安全区是否重复；
- Dynamic Type / fontScale 下是否截断；
- 键盘弹出后聚焦字段是否可见；
- 弹层焦点进入、归还与读屏顺序；
- 浅色、深色、RTL、横屏、分屏的真实表现；
- 加载、空、错误状态是否符合业务语义。

因此：

```text
Schema/lint 通过 ≠ 原生代码编译通过 ≠ 页面设计与交互验收通过
```

## 4. 四层目标架构

```text
L0 设计真源
   tokens / components / layout / a11y / content
                ↓
L1 跨端页面语义层
   Page Spec：导航、信息架构、状态、操作、组件语义
                ↓
L2 平台能力适配层
   capability profile + 平台 API cards + 原生页面模板
                ↓
L3 原生工程与验收层
   SwiftUI / Compose / Web ...
   编译、测试、截图、交互、无障碍
```

### 4.1 L0：设计真源

- `tokens/`：设计数值唯一真源；
- `contracts/`：跨端组件参数语义、受控值、槽位、默认值和兼容性契约；
- `docs/specs/`：用途、反例、视觉、状态、内容、交互和验收；
- `docs/09-layout.md`：导航骨架、间距、密度、多设备和滚动规则；
- `docs/06-accessibility.md`：无障碍硬门槛；
- `docs/07-content.md`：内容规范。

AI 默认读取由这些真源生成的任务适配产物，不全量读取原文。

### 4.2 L1：跨端页面语义层

Page Spec 回答「页面要做什么」，不回答「某平台怎么写代码」。核心内容包括：

- 用户目标与页面任务；
- 导航层级与内容模式；
- 主操作；
- 信息区域、组件或配方语义；
- loading / content / empty / error 等状态；
- 数据与空值语义，不绑定平台 State 类型；
- 跨端无障碍意图；
- 可判定的设计和业务验收；
- 必要且受限的平台 overrides。

Page Spec 不是 App 强制运行时依赖；单平台小修改可以直接走原生模板，按需补 Page Spec 供评审。详细字段和示例见 [流水线方案](02-SKILL-BUILD-PIPELINE.md#8-page-spec-契约)。

### 4.3 L2：平台能力适配层

每个平台 Provider 负责：

1. 将 Page Spec 语义映射为原生结构；
2. 提供真实公开 API 与最小编译例；
3. 提供平台导航、Insets、返回、键盘、字体缩放和效果降级；
4. 提供已验证的原生模板；
5. 声明不支持的能力与降级策略。

### 4.4 L3：原生工程与验收层

代码最终进入消费方工程或独立 AIStarter，而不是 WisdomUI 发布组件内部。

| 位置 | 负责内容 |
| --- | --- |
| 设计仓 | 规范、组件语义、Page Spec、Provider SPI、Skill 编排和跨端校验 |
| iOS / Android 实现仓 | 公开 API、平台能力、最小调用例和平台验证 |
| 消费方 App / AIStarter | 业务页面、导航、状态、数据、黄金页面和消费侧测试 |
| 组件库 Demo | 组件组合参考，不直接作为业务页面真源 |

## 5. 组件知识模型：一份语义，多份平台 API

```text
Button
├── semantic-card        跨端用途、层级、状态、内容与反例
├── ios-api-card         SwiftUI 真实构造、Modifier、类型与示例
├── android-api-card     Compose 真实签名、状态、Modifier 与示例
└── web-api-card         仅在未来存在真实 Web 实现时提供
```

| 数据 | 加载方式 | 用途 |
| --- | --- | --- |
| 轻量组件目录 | 短行目录或有限候选 | 选择组件、识别反例和替代方案 |
| 组件语义卡 | 按组件加载 | 判断状态、内容、交互和跨端设计规则 |
| 平台 API 卡 | 按平台 + 组件 + 版本加载 | 生成真实原生代码 |
| 平台能力画像 | 每任务只加载目标平台 | 约束导航、Insets、返回、键盘、无障碍和降级 |
| 原生页面模板 | 每任务选择一个 | 提供可编译结构，减少重复生成 |

真源职责：

```text
设计 specs
    → 为什么用、何时用、应该呈现什么

contracts/*.yaml
    → 跨端语义、受控值、枚举与兼容性是否一致

平台源码 / symbol graph / API dump
    → 当前平台能否这样调用

消费方工程编译与测试
    → 页面是否真正可运行、表现是否合格
```

37 个设计组件不等于两个平台都已有 37 个可用实现。设计覆盖、API 发现、最小编译、模板验证和运行时验证分别统计；缺实现时显式降级，不自动补造组件。

## 6. 平台适配不等于名称映射

| 能力 | iOS | Android | Web / H5（未来 Provider） |
| --- | --- | --- | --- |
| 导航 | NavigationStack、返回手势 | NavController、系统 / 预测式返回 | History / Router、浏览器返回 |
| 安全区 | Safe Area | WindowInsets | `env(safe-area-inset-*)` 与视口 |
| 字体缩放 | Dynamic Type | `fontScale` | 浏览器字号与页面缩放 |
| 玻璃效果 | 系统能力 + 版本降级 | 实底或明确库能力降级 | CSS 能力检测与性能降级 |
| 列表 | ScrollView / Lazy 容器 | LazyColumn 等 | 虚拟列表与语义 DOM |
| 触控目标 | ≥44pt | ≥48dp | CSS px，结合指针类型与平台规则 |
| 键盘 | FocusState + 滚动避让 | IME Insets | VisualViewport / 焦点滚动 |
| 状态 | SwiftUI 状态与 Binding | 状态提升、remember / saveable | 框架状态与 URL / 存储策略 |
| 无障碍 | VoiceOver、AccessibilityFocus | TalkBack、语义树 | 键盘、焦点、ARIA |
| 图标 | SF Symbols 语义名 | 调用方 ImageVector | SVG / Web 图标映射 |

同一设计意图应使用各平台地道的实现，不能为了 API 对称而消除平台正常行为。能力字段、证据和验证状态由 Provider 管理，详见 [Provider SPI](02-SKILL-BUILD-PIPELINE.md#7-provider-spi)。

## 7. 推荐生成流程

### 7.1 通用流程

```text
0. 工具识别目标平台、组件库版本、宿主工程和验证命令
1. AI 输出简短 Page Brief：
   用户目标 / 主操作 / 内容模式 / 数据状态 / 导航层级
2. 工具返回匹配的页面模板与组件候选
3. AI 选择组件；工具按需返回：
   组件语义卡 + 目标平台 capability profile + 平台 API 卡
4. 工具复制已验证的原生页面骨架
5. AI 只实现业务差异：
   数据、文案、状态、动作、组件组合
6. 自动验证：
   Page Spec / lint → 平台编译 → 快照 / UI 状态矩阵
7. 输出：
   可运行代码 + 验证结果 + 未验证项
8. 需要跨端交接时输出 Page Spec，而不是反向限制所有原生代码
```

### 7.2 三种模式

- **Design**：需求 → Page Brief → Page Spec → 跨端结构校验，不加载平台 API；
- **Single Platform**：选择页面模式和 Provider → 原生模板 → 业务差异 → 平台验证，Page Spec 按需生成；
- **Cross Platform**：同一 Page Spec 分别进入 iOS / Android Provider，各自生成和验证，不从一端代码机械翻译另一端。

### 7.3 验收分层

| 层级 | 证明内容 |
| --- | --- |
| Spec / lint | 页面语义、组件存在性、允许的结构 |
| 原生编译 | 真实 API、类型、泛型、状态和平台版本 |
| 快照 / UI | 视觉、遮挡、键盘、焦点、读屏和交互 |
| 人工设计评审 | 信息架构、业务合理性、视觉重量与内容质量 |

每层独立报告，前一层通过不能覆盖后一层未执行。

## 8. Token 优化：减少检索、输出和修复

### 8.1 按需加载

```text
常驻：
  精简 AI 入口 + 任务路由 + 硬规则

按任务：
  一个导航骨架 + 一个内容模式
  + 本次组件语义卡
  + 目标平台 capability profile
  + 选中组件的平台 API 卡

不加载：
  非目标平台 API
  评审与审计历史
  HTML 画廊源码
  完整 tokens
  完整组件实现
```

### 8.2 优先确定性检索

- 组件名、API、枚举、图标和版本使用结构化精确查询；
- 业务语义到组件候选使用关键词 / 轻量索引；
- 向量检索只能补语义候选，不能替代真实 API；
- 首版不急于建设复杂 RAG 或 MCP 服务。

### 8.3 减少生成和修复

- 工具复制原生模板，模型不重复输出骨架；
- 已有页面修改优先生成局部 diff；
- 固定格式化、目录和命名；
- 稳定上下文按组件库版本缓存；
- 编译错误只返回相关错误和有限源码片段；
- 自动修复有轮次上限；
- 无法证明的能力明确报告，不反复尝试编造。

### 8.4 统一测量口径

```text
端到端成本 =
入口与规则输入 + 检索输入 + API / 模板输入 + 业务需求输入
+ 代码输出 + 错误反馈 + 修复轮次 + 工具调用成本
```

同时统计首次编译成功率、API 幻觉、设计问题、状态矩阵通过率、人工修改量和耗时。不能用整仓字符粗估或 `SKILL.md` 大小代替真实总成本，也不能在实测前承诺固定节省比例。
